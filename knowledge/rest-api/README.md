# Bitrix24 REST API Engineering Knowledge Base

Инженерная база знаний для проектирования, разработки и аудита интеграций Bitrix24. Документ не заменяет контракт конкретного метода: перед реализацией необходимо сверять версию REST, параметры, scope, тариф, права и фактическую конфигурацию портала по [официальной документации](https://apidocs.bitrix24.ru/) и [справочнику API](https://apidocs.bitrix24.ru/api-reference/).

> **Обозначения:** «Подтверждённая возможность» означает обобщение официальной документации. «Рекомендация архитектора» — инженерное решение, которое нужно адаптировать к проекту. Точный числовой лимит, не зафиксированный в используемых источниках, в документе не приводится.

> **Безопасность:** все примеры синтетические и не выполнялись. Домены, токены и идентификаторы — плейсхолдеры. Секреты, персональные данные, реальные payload и клиентские выгрузки хранить в Git запрещено.

## 1. Архитектура REST API Bitrix24

REST API — контракт между Bitrix24 и внешним приложением для чтения и изменения доступных сущностей, обработки событий, встраивания интерфейса и автоматизации. Запрос выполняется по HTTPS к endpoint портала или API, содержит имя метода, параметры и авторизационный контекст; ответ обычно возвращается в JSON. Точный путь и формат зависят от версии REST и способа авторизации.

### 1.1. Модели взаимодействия

| Модель | Назначение | Архитектурное замечание |
|---|---|---|
| Входящий вебхук | Быстрый серверный вызов разрешённых методов от имени создавшего пользователя | Секрет встроен в URL; подходит для ограниченной интеграции одного портала |
| OAuth-приложение | Делегированный доступ с управляемым жизненным циклом токенов | Требует безопасного хранения и обновления токенов, обработки установки и отзыва |
| Локальное приложение | Решение для конкретного портала | Выбор клиентской или серверной реализации зависит от сценария и официально поддерживаемого типа приложения |
| Тиражное приложение | Установка на несколько порталов, обычно через Маркетплейс | Нужны multi-tenant изоляция, onboarding, обновления, поддержка и отзыв доступа |
| Серверная интеграция | Фоновая обработка, очереди, ETL, события | Секреты и бизнес-логика остаются на доверенном сервере |
| Клиентская интеграция | UI внутри или рядом с Bitrix24 | Нельзя помещать долгоживущие секреты в браузер; доступ ограничивается официальным клиентским механизмом |

Официальная документация различает REST и REST 3.0. Перед разработкой фиксируется версия API, поскольку пути, формат ответа и состав методов могут различаться.

### 1.2. Cloud и On-Premise

**Cloud:** доступны официальные REST-механизмы, вебхуки и приложения в пределах тарифа, прав, доменной зоны и опубликованных возможностей. Доступа к ядру, серверному PHP и базе данных нет.

**On-Premise:** REST также применяется как поддерживаемый интеграционный слой. Дополнительно возможны серверные расширения и инфраструктурные механизмы коробки, но они не являются REST API. Их доступность зависит от версии продукта и модулей; ядро изменять нельзя. Источник: [документация коробочного Bitrix24](https://dev.1c-bitrix.ru/docs/portal.php).

### 1.3. Границы ответственности

| Bitrix24 | Внешний сервис |
|---|---|
| Проверяет авторизацию и права, выполняет опубликованный метод, возвращает результат или ошибку | Безопасно хранит секреты, валидирует вход, соблюдает лимиты, тайм-ауты и контракт |
| Управляет доступностью продукта и поведением конкретной версии API | Обеспечивает retry, идемпотентность, очереди, мониторинг, mapping и восстановление |
| Хранит CRM-данные в рамках настроек портала | Определяет мастер-систему, правила конфликтов и минимизацию персональных данных |

## 2. Способы авторизации

| Способ | Когда использовать | Когда не использовать | Преимущества | Ограничения и риски | Поддержка |
|---|---|---|---|---|---|
| Входящий вебхук | Один портал, ограниченная серверная интеграция, быстрый прототип или внутренний read-only инструмент | Тиражное решение, браузерный код, сложный жизненный цикл пользователей | Простая настройка и вызов | Секрет в URL; права связаны с владельцем; утечка URL даёт доступ в рамках разрешений | Ротация, отзыв, минимальный scope, отдельный владелец, журнал использования |
| OAuth 2.0 | Приложение, multi-tenant, управляемая установка и делегированный доступ | Когда достаточно локального ограниченного вебхука и OAuth неоправданно усложняет эксплуатацию | Стандартный жизненный цикл доступа | Истечение/обновление токенов, отзыв, tenant isolation, защита redirect flow | Шифрование токенов, refresh-процесс, аудит установок и отзывов |
| Локальное приложение | Кастомизация одного портала с официальными точками встраивания или серверной логикой | Массовое распространение без отдельного процесса установки | Контекст конкретного портала | Зависимость от настроек портала и типа приложения | Версионирование, документация установки, совместимость |
| Тиражное приложение | Повторяемый продукт для нескольких порталов | Разовая внутренняя интеграция | Централизованное обновление и масштабирование | Multi-tenant безопасность, модерация, поддержка разных конфигураций | Onboarding, SLA, миграции, мониторинг на tenant |
| OAuth access token пользователя | Внутри подтверждённого OAuth-сценария от имени пользователя | Как самостоятельно придуманный «вечный пользовательский токен» | Делегированные права | Срок жизни, отзыв, изменение прав пользователя | Проверять официальный grant и правила refresh для выбранного приложения |
| Server-to-server | Фоновый обмен между доверенными backend-системами через поддерживаемый webhook/OAuth-контекст | Если нужен интерактивный выбор пользователя | Очереди, централизованные секреты и наблюдаемость | В Bitrix24 не следует предполагать отдельный универсальный grant без подтверждения документацией | Выбрать официально поддерживаемый webhook или OAuth-сценарий |

**Рекомендация архитектора:** секреты хранятся в secret manager или переменных окружения, но не в репозитории. `.env` допустим только локально и исключён из Git; `.env.example` содержит фиктивные значения.

## 3. Структура REST-запроса

| Элемент | Правило |
|---|---|
| Endpoint | Формируется по официальному сценарию авторизации и версии REST; не собирать путь по памяти |
| Method | Имя опубликованного метода, например из семейства CRM; наличие проверять в справочнике |
| Parameters | Передавать только документированные параметры с валидными типами |
| Required/optional | Проверять на странице конкретного метода; «поле есть в карточке» не означает, что оно обязательно или доступно через REST |
| Response | Валидировать HTTP-статус и JSON-схему; не считать наличие HTTP 200 достаточным без проверки ошибки в payload |
| Errors | Сохранять безопасный код, категорию, correlation ID и retry decision |
| Pagination | Итерировать по маркеру продолжения, который фактически вернул метод |
| Batch | Набор именованных команд; каждая команда имеет самостоятельный результат или ошибку |
| Filter | Использовать только поддерживаемые операторы и поля; семантика зависит от метода |
| Order | Задавать стабильную сортировку, особенно при инкрементальной выборке |
| Select | Запрашивать минимальный набор полей; поведение обязательных системных полей проверять |
| Encoding | HTTPS и UTF-8; корректно кодировать URL/form/JSON в соответствии с методом и клиентом |
| Date/time | Передавать документированный формат, хранить UTC или явный offset, фиксировать часовой пояс портала |
| User fields | Сначала получать метаданные полей; внутренние коды стабильнее отображаемых названий |

Официальные страницы по форматам, ответам, ошибкам, pagination и batch находятся в [REST-документации](https://apidocs.bitrix24.ru/).

Ниже приведены группы возможностей, а не исчерпывающий перечень методов. Точное наличие операции проверяется в [справочнике API](https://apidocs.bitrix24.ru/api-reference/).

| Задачи | Задачи, участники, сроки и связанные возможности | Версии методов и поддержка отдельных подобъектов различаются |
| Пользователи | Пользователь и организационный контекст | Минимизация персональных данных и проверка прав |
| Диск | Хранилища, папки, файлы и права | Размеры, форматы передачи и доступ проверять по методу |

## 5. CRM REST

### 5.1. Базовые операции

| Операция | Инженерное правило |
|---|---|
| `add` | Валидировать вход; сохранить внешний ID и возвращённый ID; повтор не должен создавать дубль |
| `get` | Обрабатывать отсутствие объекта и запрет доступа как разные случаи |
| `list` | Ограничить `select`, задать фильтр и стабильную сортировку, пройти всю pagination |
| `update` | Отправлять только управляемые поля; не перезаписывать параллельные изменения без стратегии конфликтов |
| `delete` | По умолчанию не автоматизировать; требуются согласование, dry-run, зависимости и откат |
| `fields` | Использовать для актуального mapping и валидации, а не хранить вечную копию схемы |

Пользовательские поля идентифицируются внутренними кодами. Перед записью проверяются тип, множественность, допустимые значения и права. Связи сущностей, реквизиты, товары, timeline и activities имеют отдельные контракты; их нельзя считать обычными полями карточки.

### 5.2. Классические и универсальные методы

| Подход | Применение | Преимущество | Риск |
|---|---|---|---|
| Классические семейства, например `crm.lead.*`, `crm.deal.*`, `crm.contact.*`, `crm.company.*` | Стандартные CRM-сущности, когда нужная операция официально опубликована | Явная предметная семантика | Разные контракты по сущностям и legacy-особенности |
| Универсальные `crm.item.*` | Смарт-процессы и поддерживаемые универсальной моделью CRM-типы | Общий контракт для элементов | Требуется корректный `entityTypeId`; не все особенности классической сущности обязаны совпадать |

**Рекомендация архитектора:** выбирать подход по официальному контракту целевой сущности, а не пытаться искусственно унифицировать все операции. Для счетов и новых типов особенно важно проверить фактическую модель портала.

## 6. Смарт-процессы и универсальные методы

| Понятие | Значение и контроль |
|---|---|
| `entityTypeId` | Идентификатор типа CRM-объекта; хранить как конфигурацию, а не угадывать |
| Factory/type | Метаданные пользовательского типа, его возможности и настройки; доступные REST-операции проверять |
| Item | Экземпляр типа, обрабатываемый универсальными методами `crm.item.*` |
| Stages | Стадии зависят от типа и категории; mapping должен учитывать направление/категорию, если применимо |
| Fields | Системные и пользовательские поля; схема получается из официального metadata-контракта |
| Relations | Связи с CRM-объектами проектируются явно; не хранить только отображаемое имя |
| Automation | Роботы, триггеры и БП зависят от включённых возможностей и тарифа |
| Permissions | Проверять под реальным интеграционным пользователем, не только администратором |

Официальная пользовательская основа: [Как создать смарт-процесс в CRM](https://helpdesk.bitrix24.ru/open/18913884/). Ограничения пользовательских типов, factory и REST-полей требуют проверки по конкретному порталу и [API](https://apidocs.bitrix24.ru/api-reference/).

## 7. Batch-запросы

Batch объединяет несколько REST-команд в один запрос и может связывать команды через результаты предыдущих. Точный синтаксис и актуальные ограничения проверяются в официальной документации; числовой предел в этом документе намеренно не фиксируется.

### 7.1. Правила применения

- каждая команда имеет стабильное имя;
- результат и ошибка проверяются для каждой команды отдельно;
- зависимая команда не должна выполняться, если исходная дала некорректный результат;
- retry повторяет только безопасную или неподтверждённую часть;
- batch не превращает набор действий в транзакцию;
- порядок и `halt`-поведение задаются осознанно по документированному контракту.

### 7.2. Когда не применять

- операция требует атомарности всей пачки;
- одна команда передаёт большой файл или тяжёлый payload;
- команды имеют сложную ветвящуюся зависимость;
- невозможно безопасно определить уже выполненную часть;
- обычная очередь даёт лучшую управляемость и наблюдаемость.

### 7.3. Архитектура массовой операции

```text
Source → Normalize → Validate → Dry-run report → Approval
       → Queue → Batch builder → Bitrix24 REST
       → Per-command result → Checkpoint → Reconciliation report
       → Retry queue / Manual review
```

Пример не содержит токенов и не является выполненным запросом. Пачка формируется только после dry-run; каждый элемент имеет `operation_id`, внешний ключ и состояние `planned/sent/succeeded/failed/unknown`.

## 8. Пагинация и большие объёмы данных

В REST v2 списочные методы могут использовать `start`, а ответ — возвращать `next` и иногда `total`. REST 3.0 может иметь отличающийся контракт. Интеграция должна следовать фактическому ответу выбранного метода, а не предполагать одинаковую pagination везде.

### 8.1. Надёжный обход

1. Задать минимальный `select`, фильтр и стабильный `order`.
2. Сохранить параметры выборки и время начала snapshot.
3. Запросить страницу.
4. Обработать элементы идемпотентно.
5. Сохранить `next`/cursor и последний устойчивый ключ как checkpoint.
6. Продолжать до отсутствия маркера следующей страницы.
7. Выполнить reconciliation по количеству и выборке.

`total` может быть дорогим или отсутствовать; не строить цикл только на нём. Для инкрементальной синхронизации используется документированное поле изменения и tie-breaker по ID. Граница времени перекрывается безопасным окном, а повторы устраняются по ID и версии/времени изменения.

Checkpoint содержит tenant, сущность, версию алгоритма, фильтр, cursor, последнюю дату, последний ID и статус пачки. Логи не содержат payload с персональными данными.

## 9. Ограничения и производительность

Bitrix24 применяет ограничения интенсивности и ресурсоёмкости REST. Актуальные правила нужно сверять в [официальной документации](https://apidocs.bitrix24.ru/); точные числа здесь не фиксируются.

| Механизм | Рекомендация архитектора |
|---|---|
| Timeout | Отдельные connect/read/overall timeouts; бесконечное ожидание запрещено |
| Retry | Только для временных и сетевых сбоев; ограниченное число попыток |
| Exponential backoff | Увеличение паузы с jitter, учёт серверной рекомендации ожидания, если она возвращена |
| Queue | Разделяет приём события и REST-вызов, ограничивает конкуренцию и хранит состояние |
| Parallelism | Лимит на tenant и тип операции; адаптация при росте ошибок/задержки |
| Cache | Только для безопасных метаданных с TTL и инвалидированием; права и динамические данные не кешировать бесконтрольно |
| Monitoring | Частота, latency, error rate, throttling, backlog, age и результат синхронизации |
| Degradation | При сбое внешнего сервиса принимать события в очередь, останавливать небезопасные записи, сохранять возможность восстановления |

## 10. Идемпотентность и защита от дублей

- Назначить внешний ID для каждой синхронизируемой сущности.
- Определить состав уникального ключа в пределах tenant и типа объекта.
- Перед `add` искать по надёжному ключу, но учитывать гонку между параллельными worker.
- Реализовать upsert как контролируемую последовательность find → decide → add/update → verify.
- Хранить соответствие `external_id ↔ bitrix24_id` в интеграционном реестре.
- Для события вычислять или сохранять `event_id`; при отсутствии гарантированного ID — детерминированный ключ из разрешённых атрибутов.
- Retry выполнять с тем же `operation_id`, а не создавать новую операцию.
- Не считать timeout доказательством невыполнения: сначала выполнить read-after-timeout/reconciliation.
- Частично выполненная операция переходит в `unknown` или `partial`, а не безусловно повторяется.

## 11. События и вебхуки

Исходящий поток событий строится как минимум в два шага: быстрый приём и асинхронная обработка. Подписка выполняется только на официально поддерживаемое событие и с минимальными правами.

```text
Bitrix24 event → HTTPS receiver → validation → durable queue → worker
               → deduplication → REST enrichment/update → audit log
```

### Контроль

- входящий вебхук — credential для вызова Bitrix24; исходящее событие — уведомление из Bitrix24 во внешний endpoint;
- точную модель подписи события нельзя предполагать: поддержка и алгоритм проверяются для конкретного типа приложения и события;
- если подпись не предусмотрена подтверждённым контрактом, применяются секретный непредсказуемый endpoint, HTTPS, allowlist только если официально и инфраструктурно применимо, а также последующая проверка данных через REST;
- повторная доставка и изменение порядка считаются возможными;
- endpoint быстро подтверждает приём только после надёжной постановки в очередь;
- ошибки обработки попадают в retry или dead-letter queue;
- мониторятся last event time, lag, duplicates, failures и backlog.

## 12. Безопасность

| Область | Требование |
|---|---|
| Токены | Шифрование at rest, доступ только runtime-роли, отсутствие в Git и логах |
| `.env` | Только локально, исключён из Git; production использует secret manager |
| Права | Минимальные scope и отдельный интеграционный пользователь |
| Персональные данные | Минимизация, правовое основание, маскирование, сроки хранения и контроль экспорта |
| Логи | Метаданные операции вместо полного request/response; секреты редактируются до записи |
| Ротация | Документированная замена без простоя и отзыв старого credential |
| Отзыв | Runbook на компрометацию, отключение приложения/вебхука и проверку журнала |
| IP restrictions | Использовать только если механизм подтверждён для выбранного сценария; не считать единственной защитой |
| Аудит | Кто, когда, каким приложением и какую категорию операции выполнял |
| Утечка webhook | Считать утечкой credential; немедленно отозвать, выпустить новый и проверить действия |

Клиентский браузер не должен получать секрет, предназначенный серверу. Пример в документации никогда не содержит настоящий endpoint.

## 13. Обработка ошибок

| Категория | Как распознать | Retry | Логирование | Ручное вмешательство |
|---|---|---|---|---|
| HTTP-ошибка | Неуспешный HTTP status или некорректный transport-response | По категории status и идемпотентности | status, method group, correlation ID | При устойчивом ответе или неизвестном результате записи |
| Авторизация | Официальный код/сообщение invalid/expired credential | После корректного refresh, не бесконечно | Без токена; tenant и auth flow | Если refresh/reinstall невозможны |
| Права | Access denied при валидной авторизации | Нет без изменения прав | Пользователь, scope-класс, операция | Владелец портала согласует минимальные права |
| Параметры | Ошибка валидации метода | Нет | Безопасная схема входа и имя поля | Исправить mapping или данные |
| Сущность отсутствует | Документированный not found/пустой результат | Обычно нет | Тип и обезличенный ID | Если объект ожидался по контракту |
| Временная серверная | Временный/недоступный сервис | Да, ограниченно с backoff | attempt, latency, response class | При исчерпании retry/SLA |
| Лимит | Ответ ограничения интенсивности/ресурса | Да после ожидания | tenant, method, concurrency | При систематическом превышении — изменить архитектуру |
| Конфликт данных | Версия/состояние изменились между чтением и записью | Только после повторного чтения и policy | обе версии без чувствительных полей | Неопределённое правило конфликта |
| Частичный batch | Некоторые команды успешны, другие нет | Только выбранные команды | результат каждой команды | Если зависимость дала неоднозначный итог |
| Сетевая ошибка | DNS/connect/reset/timeout | Read — обычно да; write — после проверки состояния | стадия сети, elapsed, operation ID | Неизвестный результат небезопасной записи |

Никогда не скрывать исключение пустым `catch`. Ошибка получает классификацию `retryable`, `permanent`, `manual` или `unknown`.

## 14. Архитектурные паттерны интеграций

| Паттерн | Когда использовать | Преимущества | Риски и поддержка |
|---|---|---|---|
| Синхронный запрос | Пользователь ждёт короткую операцию | Простая обратная связь | Тайм-аут влияет на UX; не подходит для массовой обработки |
| Асинхронная очередь | Долгие, массовые или событийные операции | Backpressure, retry, восстановление | Нужны worker, DLQ, дедупликация и мониторинг |
| ETL | Периодическая миграция или аналитическая выгрузка | Контролируемые стадии transform/reconcile | Устаревание данных и большие объёмы |
| Двусторонняя синхронизация | Обе системы действительно изменяют разные или согласованные поля | Доступность данных в обеих системах | Конфликты и циклы; нужна ownership-матрица каждого поля |
| Master-data | Одна система владеет типом данных | Простое разрешение конфликтов | Ошибочный выбор мастера блокирует процесс |
| Event-driven | Важны быстрые изменения и поддерживаемые события | Низкая задержка | Повторы, порядок, потеря подписки; нужна очередь и reconciliation |
| Polling | Нет события или нужна страховочная сверка | Предсказуемость | Нагрузка и задержка; нужен incremental cursor |
| Webhook-first | Событие запускает обработку | Быстрая реакция | Нельзя полагаться только на доставку; нужна сверка |
| Hybrid | События плюс периодический polling/reconciliation | Баланс скорости и полноты | Больше компонентов и дедупликация |
| Middleware | Несколько систем и сложные правила маршрутизации | Централизация mapping и наблюдаемости | Возможная единая точка отказа; нужны HA и ownership |

## 15. Мастер-системы и конфликт данных

Мастер-система — единственный авторитетный источник конкретного типа данных или поля.

| Мастер | Типовой сценарий | Контроль |
|---|---|---|
| CRM | Ответственный, стадия продажи, коммуникации | Внешняя система читает или обновляет только явно делегированные поля |
| 1С/ERP | Номенклатура, цены, заказ, счёт, оплата, реквизиты | CRM не перезаписывает мастер-значение; хранит внешний ID и статус обмена |
| Внешний сервис | Специализированный производственный/логистический статус | CRM получает отображаемый статус и ссылку, но не имитирует мастер-логику |

Для каждого поля задаются owner, direction, timestamp semantics, version/etag если поддерживается собственной интеграцией, приоритет и способ ручного разрешения. `last write wins` допустим только как осознанное правило; часы систем должны быть синхронизированы. Все конфликты и ручные решения записываются в журнал без избыточных персональных данных.

## 16. Миграция данных

1. Зафиксировать источник, объём, владельца, окно и недопустимые потери.
2. Создать карту полей: source → transform → target → обязательность → владелец.
3. Нормализовать телефоны, email, ИНН/регистрационные данные, даты, валюты и справочники.
4. Очистить мусорные и запрещённые данные, не меняя оригинал.
5. Определить ключи дублей; название компании не использовать как единственный ключ.
6. Присвоить внешний ID и `migration_run_id`.
7. Выполнить dry-run с количеством planned/skipped/invalid/duplicate.
8. Загрузить малую синтетическую или согласованную тестовую выборку.
9. Проверить права, автоматизацию, уведомления и нежелательные побочные действия.
10. Выполнять загрузку контролируемыми пачками через очередь/checkpoint.
11. Сверить количество, суммы, связи и репрезентативную выборку.
12. Сформировать отчёт по каждой пачке и всем ошибкам.
13. Применить заранее согласованный откат или компенсирующие действия.
14. Повторный запуск выполнять идемпотентно по внешнему ID и состоянию операции.

Оригинальные клиентские файлы не изменяются. Полный импорт требует отдельного согласования после тестовой загрузки.

## 17. Тестирование интеграций

| Вид | Что проверяет |
|---|---|
| Unit | Валидация, mapping, нормализация, retry decision и дедупликация без сети |
| Integration | Реальное взаимодействие с отдельным тестовым порталом и синтетическими данными |
| Contract | Соответствие request/response опубликованной и фактической схеме |
| Sandbox/lab | Изоляция от рабочего процесса; наличие зависит от доступного тестового портала |
| Mock | Ошибки, задержки и редкие ответы; mock не заменяет contract/integration test |
| Negative | Неверные поля, права, токен, сущность, формат и лимит |
| Rerun | Повтор не создаёт дубль и корректно продолжает checkpoint |
| Permission | Каждая операция под минимальной интеграционной ролью |
| Volume | Память, очередь, throughput и лимиты на репрезентативном объёме |
| External outage | Очередь сохраняет данные, запись контролируемо останавливается |
| Recovery | Worker продолжает после сбоя без пропусков и двойной записи |
| Duplicate | Повторное событие/объект распознаётся и безопасно обрабатывается |

Критические сценарии не тестируются на реальных клиентах без согласования.

## 18. Наблюдаемость и сопровождение

- **Структурированные логи:** timestamp, environment, tenant alias, operation ID, method group, attempt, duration, result class; без токенов и payload.
- **Correlation ID:** проходит через приём события, очередь, REST-вызов и отчёт.
- **Метрики:** request rate, latency, success/error, throttling, retry, duplicate, queue depth/age, checkpoint lag.
- **Алерты:** рост permanent errors, исчерпание retry, просроченный backlog, отсутствие ожидаемых событий, нарушение SLA.
- **Журнал синхронизации:** объект, направление, внешний/CRM ID, версия, результат, безопасная причина ошибки.
- **Dashboard:** состояние tenant, сущностей, очередей и последних успешных checkpoint.
- **Dead-letter queue:** ограниченный доступ, причина, payload reference в защищённом хранилище, ручное решение.
- **Ручной повтор:** только с предварительным просмотром, тем же operation ID и аудитом.
- **SLA:** время обнаружения, реакции, восстановления и допустимое отставание данных.
- **Регламент:** владелец, дежурство, эскалация, отзыв секретов, восстановление и post-incident review.

## 21. Примеры безопасных запросов

Примеры ниже иллюстрируют структуру и **не выполнялись**. Endpoint и имена полей необходимо сверить с официальным методом. `<PORTAL_HOST>`, `<USER_ID>`, `<WEBHOOK_SECRET>`, `<ENTITY_ID>` и другие значения — плейсхолдеры.

### 21.1. GET-подобный запрос

```http
GET https://<PORTAL_HOST>/rest/<USER_ID>/<WEBHOOK_SECRET>/crm.deal.get.json?id=<ENTITY_ID>
Accept: application/json
```

Используется для чтения одной сделки через входящий вебхук. В production секретный URL нельзя писать в лог целиком.

### 21.2. POST-запрос

```http
POST https://<PORTAL_HOST>/rest/<USER_ID>/<WEBHOOK_SECRET>/crm.deal.add.json
Content-Type: application/json; charset=utf-8

{
  "fields": {
    "TITLE": "Synthetic opportunity",
    "CURRENCY_ID": "<CURRENCY_CODE>"
  }
}
```

Перед записью dry-run валидирует поля, валюту, права и ключ идемпотентности. Полный обязательный набор зависит от портала и требует проверки.

### 21.3. List с pagination

```text
cursor = 0
do:
  response = call("crm.deal.list", {
    "order": {"ID": "ASC"},
    "filter": {">ID": last_processed_id},
    "select": ["ID", "DATE_MODIFY"],
    "start": cursor
  })
  process_idempotently(response.result)
  save_checkpoint(response.next, last_processed_id)
  cursor = response.next
while cursor exists
```

Это псевдокод. Конкретный контракт `start/next` проверяется для выбранной версии метода.

### 21.4. Update

```http
POST https://<PORTAL_HOST>/rest/<USER_ID>/<WEBHOOK_SECRET>/crm.deal.update.json
Content-Type: application/json; charset=utf-8

{
  "id": "<ENTITY_ID>",
  "fields": {
    "<DOCUMENTED_FIELD_CODE>": "<SYNTHETIC_VALUE>"
  }
}
```

Интеграция отправляет только управляемое поле и сначала проверяет конфликт с текущей версией данных.

### 21.5. Batch

```json
{
  "halt": 0,
  "cmd": {
    "read_first": "crm.deal.get?id=<ENTITY_ID_1>",
    "read_second": "crm.deal.get?id=<ENTITY_ID_2>"
  }
}
```

Payload отправляется документированным способом методу `batch`. Формат кодирования, подстановка результатов и актуальные ограничения проверяются в официальной документации. Каждая команда оценивается отдельно.

### 21.6. Обработка ошибки и retry

```text
try:
  response = call_with_timeout(operation)
  validate_http_and_api_response(response)
catch error:
  category = classify(error)
  log_safe_metadata(operation_id, category, attempt)
  if category is retryable and operation_is_safe:
    schedule_retry_with_backoff_and_jitter()
  else if result_is_unknown:
    schedule_reconciliation()
  else:
    send_to_manual_review()
```

Псевдокод подчёркивает, что retry определяется типом ошибки и идемпотентностью, а не выполняется автоматически для любого исключения.

### 21.7. Dry-run

```text
input → normalize → validate → deduplicate → permission check
      → planned changes report
      → no REST write calls
```

Dry-run возвращает количества `planned`, `unchanged`, `duplicate`, `invalid`, `forbidden` и выборку предполагаемых изменений без секретов и персональных данных.

## 22. Cloud vs On-Premise

| Возможность | Облако | Коробка | Комментарий интеграционного архитектора |
|---|---|---|---|
| REST API | Доступен по официальному контракту и ограничениям сервиса | Доступен с учётом версии модулей | Версии и методы проверять на целевом портале |
| OAuth | Для поддерживаемых приложений | Зависит от версии и конфигурации | Не проектировать flow без проверки документации |
| Локальные приложения | В рамках официальных возможностей портала и тарифа | В рамках версии продукта | Клиентская/серверная модель выбирается по сценарию |
| Серверный код внутри портала | Недоступен | Возможен через поддерживаемые расширения | Ядро не изменять |
| События | Поддерживаемые REST-события | REST-события плюс возможные коробочные механизмы | Контракт, повторы и права проверять отдельно |
| Доступ к базе | Нет | Технически контролируется владельцем | Прямая запись в БД не является безопасным REST-паттерном |
| Расширение ядра | Нет | Запрещено как поддерживаемый подход | Использовать модули и события расширения |
| Очереди | Во внешнем сервисе | Во внешнем сервисе или инфраструктуре коробки | Durable queue предпочтительна для массовых операций |
| Cron/агенты | Не управляются клиентом | Управляются владельцем | Нужны мониторинг и регламент запуска |
| Логирование | Внешние логи и доступные средства приложения | Дополнительно серверные журналы | Везде маскировать секреты и персональные данные |
| Контроль инфраструктуры | У поставщика | У владельца | Коробка требует backup, capacity planning и обновлений |
