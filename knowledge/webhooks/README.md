# Bitrix24 Webhooks Engineering Knowledge Base

Инженерная база знаний для проектирования, защиты, внедрения и аудита webhook-интеграций Bitrix24. Документ не заменяет контракт конкретного REST-метода или события: версия API, параметры, scope, доступность и формат доставки проверяются по [официальной документации](https://apidocs.bitrix24.ru/) на целевом портале.

> **Разделение сведений:** «Подтверждённый факт» — инженерное резюме официальных источников из `knowledge/SOURCES.md`. «Рекомендация архитектора» — проектное решение. Наличие подписи, повторной доставки, IP-фильтрации или конкретного события нельзя предполагать без проверки опубликованного контракта.

> **Безопасность:** примеры синтетические и не выполнялись. Реальные домены, webhook URL, токены, payload, персональные данные и клиентские выгрузки хранить в Git запрещено.

## 1. Что такое Webhooks

Webhook — механизм интеграции, в котором HTTP endpoint используется либо как credential для вызова REST API Bitrix24, либо как адрес доставки поддерживаемого события во внешнюю систему. Эти направления имеют разную модель доверия и не должны смешиваться.

| Аспект | Подтверждённый факт | Рекомендация архитектора |
|---|---|---|
| Входящий webhook | Даёт URL для вызова разрешённых REST-методов от имени связанного пользователя | Считать URL секретом уровня API credential |
| Исходящая доставка | Bitrix24 может передавать данные о поддерживаемом событии во внешний endpoint в подтверждённом сценарии | Принимать быстро, ставить в durable queue, обрабатывать идемпотентно |
| REST-события | Приложения могут работать с опубликованными событиями и обработчиками | Точный event name и способ подписки проверять в API |
| Область применения | Интеграции одного портала и событийные сценарии | Для тиражного multi-tenant продукта обычно оценивать OAuth-приложение |

```text
Webhook integration = credential path OR event delivery path
                      ≠ arbitrary callback without a published contract
```

Практическое правило: сначала определить направление потока, владельца данных, событие, права и последствия повторного вызова.

## 2. Входящие и исходящие Webhooks

| Критерий | Входящий webhook | Исходящий webhook / событие |
|---|---|---|
| Инициатор HTTP | Внешняя система | Bitrix24 |
| Получатель | REST endpoint Bitrix24 | Endpoint внешней системы |
| Основная цель | Вызвать разрешённый REST-метод | Сообщить о поддерживаемом событии |
| Секрет | Обычно включён в URL входящего webhook | Модель проверки отправителя зависит от подтверждённого контракта |
| Основной риск | Утечка URL и избыточные права | Подделка, повторы, изменение порядка, недоступность receiver |
| Ответственность | Клиент соблюдает REST-контракт и лимиты | Receiver валидирует, сохраняет и асинхронно обрабатывает событие |

```text
Incoming: External Service ──HTTPS REST call──> Bitrix24
Outgoing: Bitrix24 ──HTTPS event delivery──> Receiver ──> Queue ──> Worker
```

Практическое правило: термин «исходящий webhook» в конкретной настройке может означать отдельный продуктовый механизм или REST-событие. Перед ТЗ зафиксировать официальный способ настройки и формат payload.

## 3. Архитектура работы

### 3.1. Вызов REST

| Компонент | Ответственность |
|---|---|
| Producer | Формирует валидную команду и operation ID |
| Secret store | Выдаёт webhook URL только runtime-процессу |
| REST client | Кодирует параметры, задаёт timeout, проверяет HTTP и API-ошибку |
| Queue | Ограничивает нагрузку и хранит состояние массовой операции |
| Reconciliation | Проверяет неизвестные и частичные результаты |

```text
Business event → Validate → Queue → Rate-controlled worker
               → Bitrix24 REST → Per-operation result → Checkpoint/report
```

### 3.2. Приём события

| Компонент | Ответственность |
|---|---|
| HTTPS receiver | Принимает запрос, ограничивает размер и время обработки |
| Validator | Проверяет структуру и доступный механизм подлинности |
| Durable queue | Фиксирует событие до подтверждения приёма |
| Deduplicator | Блокирует повторное бизнес-действие |
| Worker | Обогащает данные через REST и применяет идемпотентную логику |
| DLQ | Хранит необработанные события для безопасного разбора |

```text
Bitrix24 → Receiver → Validate → Durable queue → Deduplicate
                                       └──────→ Worker → REST/read/write
                                                   └──→ Retry or DLQ
```

Практическое правило: receiver не выполняет длительную бизнес-логику до постановки события в надёжную очередь.

## 4. Авторизация и безопасность

| Мера | Подтверждённый контекст | Рекомендация архитектора |
|---|---|---|
| HTTPS | REST и callback должны использовать защищённый транспорт | Запретить downgrade и проверить сертификат |
| Минимальные права | Webhook вызывает методы в рамках выданных прав и контекста пользователя | Отдельный технический владелец и минимальный scope |
| Secret storage | Webhook URL нельзя публиковать | Secret manager; `.env` только локально и вне Git |
| Подпись события | Применимость зависит от типа события/приложения | Не придумывать алгоритм; проверить официальный контракт |
| IP allowlist | Применимость не универсальна | Использовать только как дополнительную меру после подтверждения стабильных требований |
| Логи | Нужны для аудита | Маскировать URL, токены, персональные поля и тела запросов |
| Ротация | Скомпрометированный доступ должен быть отозван | Runbook отзыва, новый credential и анализ действий |

```text
Secret manager → runtime only
Git / ticket / chat / logs ─X→ webhook credential
```

Практическое правило: утечка одного полного webhook URL рассматривается как инцидент безопасности, даже если неизвестно, использовался ли он.

## 5. Получение и отзыв Webhook

Создание входящего webhook выполняется через доступный раздел разработчика портала с выбором владельца и прав. Точный путь интерфейса может меняться; сверять с [официальной документацией](https://apidocs.bitrix24.ru/).

| Этап | Обязательный контроль |
|---|---|
| Запрос | Владелец интеграции, цель, методы, данные, срок и среда |
| Создание | Минимальные права и отдельный пользователь, если организационно допустимо |
| Передача | Только через защищённый канал/secret manager |
| Проверка | Один безопасный read-only вызов на тестовом портале |
| Эксплуатация | Учёт владельца, даты, систем-потребителей и последней проверки |
| Отзыв | Отключить/удалить credential штатным способом и остановить клиентов |
| Ротация | Выпустить новый, переключить, проверить, затем отозвать старый |

```text
Request → Approval → Create → Store securely → Test → Monitor
        → Rotate / Revoke → Verify access denied → Close incident/change
```

Практическое правило: не пересылать webhook в мессенджере и не вставлять в задачу. После отзыва проверить, что старый credential больше не работает, не раскрывая его в отчёте.

## 6. Работа с REST через Webhook

Входящий webhook — способ авторизации REST-вызова, а не отдельный набор методов. Доступны только опубликованные методы, разрешённые scope и правами пользователя. Контракт проверяется в [справочнике REST API](https://apidocs.bitrix24.ru/api-reference/).

| Элемент вызова | Правило |
|---|---|
| Endpoint | Использовать выданный URL как неделимый секрет; не конструировать по памяти |
| Method | Только опубликованное имя метода |
| Parameters | Только документированные поля и типы |
| Response | Проверять HTTP status, JSON, result/error и структуру |
| Pagination | Следовать фактическому `next`/cursor выбранной версии |
| Batch | Проверять результат каждой команды; batch не является транзакцией |
| Timeout/retry | Явные timeout; retry только временных безопасных операций |
| Idempotency | Внешний ID и operation ID для записей |

```text
Webhook URL + documented method + validated parameters
    → HTTP response + API result/error
    → classify → success / retry / reconcile / manual review
```

Практическое правило: для массовой операции сначала dry-run, затем малая выборка, очередь, checkpoint и итоговая сверка. Подробная модель — в `knowledge/rest-api/README.md`.

## 7. Ограничения Cloud и On-Premise

| Область | Cloud | On-Premise | Рекомендация архитектора |
|---|---|---|---|
| REST webhooks | В пределах тарифа, прав и доступных инструментов | В пределах редакции и версии REST-модулей | Проверить фактический портал |
| Серверный код внутри портала | Недоступен | Возможен через поддерживаемые расширения | Не изменять ядро |
| База данных | Недоступна | Контролируется владельцем | Прямая запись не заменяет REST |
| Callback receiver | Внешняя инфраструктура | Внешняя или инфраструктура владельца | В обоих случаях HTTPS, queue и monitoring |
| Cron/agents | Не управляются клиентом | Управляются владельцем | Нужен контроль фоновых задач |
| Логи платформы | Ограничены доступными интерфейсами | Дополнительно серверные журналы | Не логировать секреты |
| Лимиты | Ограничения облачного REST | Зависят от версии и инфраструктуры | Точные числа брать только из текущего источника |
| Обновления | Управляет поставщик | Планирует владелец | Коробке нужны стенд и regression tests |

```text
Cloud: External service ↔ Published REST boundary ↔ Bitrix24 service
On-Premise: External service ↔ REST boundary ↔ Owned infrastructure
                                      └── supported modules, not core edits
```

Практическое правило: On-Premise не является разрешением обходить REST-контракт. Коробочные расширения оцениваются отдельно по [официальной документации](https://dev.1c-bitrix.ru/docs/portal.php).

## 8. Типовые сценарии интеграции

| Сценарий | Направление | Архитектура | Основной контроль |
|---|---|---|---|
| Форма сайта → CRM | Внешняя система → Bitrix24 | Validate → deduplicate → CRM add/update | Согласие, источник, внешний ID, защита от спама |
| CRM → уведомление ERP | Bitrix24 → receiver | Event → queue → ERP command | Повторы, порядок, мастер-система |
| 1С → статус оплаты | ERP → Bitrix24 | Queue → find by external ID → update | Оплата подтверждается только мастером |
| CRM → сервисный объект | Bitrix24 → middleware → внешняя система | Event + REST enrichment → idempotent create | Не создавать дубль после timeout |
| Периодическая сверка | External scheduler → Bitrix24 | Incremental list → checkpoint → reconcile | Pagination, даты, пропуски |
| Телефония | Поддерживаемое приложение/события | Официальный сценарий телефонии | Не смешивать REST и SIP без проверки; источник: [инструкция](https://helpdesk.bitrix24.ru/open/6450911/) |
| Smart Process integration | В обе стороны по ownership | `crm.item.*` + event/polling | `entityTypeId`, mapping, стадии и права |
| BI/выгрузка | Bitrix24 → аналитический контур | Read-only incremental ETL | Минимизация персональных данных и лимиты |

```text
Source → Contract adapter → Queue → Mapping → Target
                    ↘ Audit / metrics / DLQ / reconciliation
```

Практическое правило: webhook-first дополняется периодической reconciliation, если пропуск события критичен для бизнеса.

## 9. Лучшие практики

| Практика | Реализация | Проверяемый результат |
|---|---|---|
| Least privilege | Только нужные scope и пользовательская роль | Запрещённый метод действительно недоступен |
| Secret hygiene | Secret manager, редактирование URL | В Git и логах нет credential |
| Fast receiver | Валидация и durable enqueue | Callback укладывается в заданный внутренний SLA |
| Idempotency | Event/operation key, внешний ID | Повтор не меняет итог повторно |
| Retry policy | Классификация, backoff, jitter, предел | Permanent error не создаёт retry storm |
| Reconciliation | Периодическая сверка с мастером | Пропуски обнаруживаются автоматически |
| Observability | Correlation ID, метрики, алерты | Видны lag, error rate и backlog |
| Change control | README, схема, tests, changelog | Изменение воспроизводимо и откатываемо |

```text
Receive once or many times → process effectively once
Fail visibly → retry safely → reconcile eventually
```

Практическое правило: webhook-доставка рассматривается как сигнал. Перед критическим изменением worker при необходимости повторно читает актуальное состояние через REST.

## 10. Типичные ошибки

| № | Ошибка | Последствие | Профилактика |
|---:|---|---|---|
| 1 | Полный webhook URL в коде | Компрометация | Secret manager |
| 2 | URL в Git-истории | Секрет остаётся после удаления строки | Отзыв и очистка по согласованной процедуре |
| 3 | URL в логах | Доступ получает читатель логов | Маскирование до записи |
| 4 | URL в тикете или чате | Неконтролируемое распространение | Защищённый канал выдачи |
| 5 | Webhook создан администратором без причины | Избыточные права | Отдельный минимальный пользователь |
| 6 | Выданы все scope | Большой blast radius | Least privilege |
| 7 | Нет владельца credential | Некому ротировать и отзывать | Реестр интеграций |
| 8 | Нет срока проверки | Забытый доступ | Периодический review |
| 9 | Входящий и исходящий webhook смешаны | Ошибочная модель угроз | Явно зафиксировать направление |
| 10 | Подпись события придумана | Ложная защита | Только официальный алгоритм |
| 11 | Подлинность вообще не анализируется | Поддельные события | Подтверждённый механизм плюс REST-проверка |
| 12 | IP allowlist считается единственной защитой | Обход/поломка при изменении сети | Дополнительная мера после проверки |
| 13 | Receiver принимает HTTP | Перехват данных | Только HTTPS |
| 14 | Нет ограничения размера request | Exhaustion ресурсов | Web server/body limits |
| 15 | Вся логика выполняется в callback | Timeout и повторная доставка | Durable queue |
| 16 | Успех возвращается до надёжной фиксации | Потеря события | Ack после enqueue |
| 17 | Нет дедупликации | Повторные бизнес-действия | Event/operation key |
| 18 | Предполагается порядок событий | Старое состояние перезаписывает новое | Версия/дата и актуальное REST-чтение |
| 19 | Повторная доставка считается ошибкой | Ложные инциденты | Нормальная идемпотентная обработка |
| 20 | Timeout записи считается неуспехом | Дубли | Reconciliation/read-after-timeout |
| 21 | Retry всех ошибок | Шторм запросов | Классификация ошибок |
| 22 | Нет backoff и jitter | Одновременные повторы | Ограниченная стратегия retry |
| 23 | Нет timeout REST-клиента | Зависшие worker | Connect/read/overall timeout |
| 24 | Нет внешнего ID | Нельзя выполнить upsert | Устойчивый ключ |
| 25 | Название компании как ключ | Ложные совпадения | Реквизиты/внешний ID |
| 26 | Pagination не завершена | Неполная сверка | Следовать `next`/cursor |
| 27 | Batch считается транзакцией | Частичный результат игнорируется | Per-command status |
| 28 | Нет dry-run массовой операции | Повреждение данных | План и тестовая выборка |
| 29 | Реальные payload в тестах | Утечка персональных данных | Синтетические fixtures |
| 30 | Логируется полное тело | Утечка и рост логов | Safe metadata |
| 31 | Нет DLQ | Ошибки теряются | Dead-letter и runbook |
| 32 | Нет correlation ID | Нельзя проследить событие | Сквозной operation ID |
| 33 | Нет мониторинга очереди | Скрытый backlog | Depth/age alerts |
| 34 | Нет reconciliation | Тихие пропуски | Периодическая сверка |
| 35 | Ротация не тестировалась | Простой при замене | Dual-window runbook |
| 36 | Отзыв не проверен | Старый доступ остаётся | Контрольный отказ вызова |
| 37 | Один webhook используется всеми средами | Пересечение dev/prod | Отдельные credentials |
| 38 | Один webhook используется несколькими системами | Нельзя определить источник | Отдельный credential/consumer |
| 39 | Нет changelog | Неизвестна причина регрессии | Версионирование |
| 40 | Нет теста прав | Ошибка только в production | Test user и negative test |

```text
Typical failure chain:
leaked URL → excessive rights → no audit → undetected writes

Safe chain:
minimal credential → masked logs → alerts → revoke runbook
```

Практическое правило: аудит начинается с инвентаризации всех webhook credentials, владельцев, scope, потребителей и последнего успешного использования.

## 11. Производительность и ограничения

Bitrix24 применяет ограничения интенсивности и ресурсоёмкости REST; актуальные условия проверяются в [официальной документации](https://apidocs.bitrix24.ru/). Точные числа в документе не фиксируются.

| Область | Риск | Рекомендация |
|---|---|---|
| Burst событий | Queue backlog и throttling | Лимит concurrency на tenant и backpressure |
| Тяжёлый callback | Timeout | Только validate/enqueue |
| Массовый REST | Лимиты и нагрузка | Batch после проверки, минимальный `select`, checkpoint |
| Параллельные worker | Гонки и дубли | Partition key и idempotency lock |
| Большой payload | Память и персональные данные | Size limit и REST enrichment по ID |
| Деградация Bitrix24 | Retry storm | Circuit breaker, backoff, queue |
| Деградация внешней системы | Потеря/задержка | Durable storage и SLA backlog |
| Cache | Устаревшие права/поля | TTL только для безопасных метаданных |

```text
Ingress rate > processing rate → queue grows → alert → scale/throttle
Bitrix24 errors grow → reduce concurrency → backoff → recover → drain queue
```

Практическое правило: мониторить не только HTTP errors, но и business success, lag, duplicates, unknown results и reconciliation mismatch.

## 12. Диагностика и отладка

| Шаг | Что проверить | Безопасные данные в журнале |
|---|---|---|
| 1. Scope | Какое направление: REST-вызов или событие | Integration ID, environment |
| 2. Transport | DNS, TLS, HTTP status, timeout | Endpoint alias, не полный secret URL |
| 3. Auth | Credential активен, права достаточны | Owner ID/alias, scope class |
| 4. Contract | Method/event, schema, required fields | Version, field names без значений |
| 5. Queue | Enqueued, lag, retries, DLQ | Message ID, timestamps |
| 6. Idempotency | Был ли event/operation обработан | Dedup key hash |
| 7. Business result | Объект создан/обновлён один раз | Entity type и обезличенный ID |
| 8. Reconcile | Состояния систем совпадают | Counts, mismatch category |

```text
Correlation ID
  ├── receiver log
  ├── queue message
  ├── worker attempt
  ├── Bitrix24 REST call
  └── reconciliation result
```

Практическое правило: тестовый replay выполняется только синтетическим событием или безопасной ссылкой на защищённый payload. Нельзя копировать production body в репозиторий.

## 13. Практический чек-лист архитектора

| Область | Критерий готовности |
|---|---|
| Контекст | Cloud/On-Premise, зона, тариф/редакция и версия зафиксированы |
| Направление | Входящий REST или исходящее событие определено однозначно |
| Авторизация | Выбран webhook или OAuth с обоснованием |
| Права | Минимальные scope и тестовая роль подтверждены |
| Данные | Мастер-система, mapping, внешний ID и персональные данные описаны |
| Надёжность | Queue, timeout, retry, idempotency и reconciliation реализуемы |
| Безопасность | Secret manager, rotation, revoke и masked logs спроектированы |
| Эксплуатация | Метрики, алерты, DLQ, runbook и SLA имеют владельцев |
| Тестирование | Positive, negative, duplicate, outage, recovery и volume tests подготовлены |
| Изменения | README, схема, changelog и rollback актуальны |

```text
Design → Security review → Synthetic test → Pilot → Production
       → Monitor → Reconcile → Improve / Rotate / Revoke
```

### Контрольный список

- [ ] Официальный метод/событие и payload подтверждены.
- [ ] Указаны владелец, потребитель и среда credential.
- [ ] Webhook не разделяется между dev/test/prod.
- [ ] Полный URL отсутствует в Git, логах и тикетах.
- [ ] Receiver использует HTTPS и ограничивает body/time.
- [ ] Событие сохраняется в durable queue до ack.
- [ ] Повтор и изменение порядка безопасны.
- [ ] REST-записи имеют operation ID и внешний ключ.
- [ ] Частичный и неизвестный результат обрабатывается.
- [ ] Массовая операция поддерживает dry-run.
- [ ] Есть метрики latency, errors, backlog и lag.
- [ ] Подготовлены rotation/revoke и incident runbooks.
- [ ] Тесты используют только синтетические данные.
- [ ] Пилот выполняется на тестовом портале/воронке.

Практическое правило: запуск запрещается, если нет владельца поддержки, мониторинга или безопасного отзыва credential.

## 14. Сравнение Webhooks и OAuth

| Критерий | Webhook | OAuth-приложение | Что выбрать |
|---|---|---|---|
| Масштаб | Обычно конкретный портал и ограниченная интеграция | Один или много порталов по модели приложения | Multi-tenant — OAuth; локальная узкая задача — оценить webhook |
| Создание | Настройка на портале | Установка и авторизационный flow | По операционной модели |
| Credential | Секрет в URL или контексте webhook | Access/refresh tokens по подтверждённому flow | Оба требуют secret storage |
| Жизненный цикл | Ручной учёт, ротация и отзыв | Установка, refresh, отзыв и переавторизация | OAuth требует более зрелой поддержки |
| Пользовательский контекст | Связан с создавшим/назначенным контекстом | Делегированный контекст приложения/пользователя | Проверить права конкретного сценария |
| Multi-tenant isolation | Нужно строить самостоятельно; один webhook не шарить | Естественная обязанность приложения | Отдельное шифрование токенов на tenant |
| Browser use | Secret нельзя размещать в браузере | Только официальный клиентский flow | Серверная логика предпочтительна |
| Маркетплейс | Не модель распространения продукта | Поддерживаемая модель приложения | Для тиражного решения — OAuth/официальное приложение |
| Сложность | Ниже на старте | Выше из-за token lifecycle | Учитывать полную стоимость сопровождения |
| Отзыв | Отключение/удаление webhook | Отзыв установки/токенов по flow | Runbook обязателен в обоих случаях |

```text
One portal + narrow server integration ──> consider incoming webhook
Many portals / product / delegated install ──> OAuth application
Browser-only with long-lived secret ──> prohibited architecture
```

Практическое правило: простота webhook не оправдывает избыточные права или отсутствие ротации. Официальные варианты локальных интеграций: [документация Bitrix24](https://apidocs.bitrix24.ru/local-integrations/index.html).
