# Bitrix24 CRM Architecture Knowledge Base

Инженерная база знаний для проектирования, внедрения и аудита CRM Bitrix24. Документ описывает архитектурные принципы и контрольные вопросы, а не готовую конфигурацию конкретного портала.

> **Статус сведений:** возможности продукта следует подтверждать по официальной [пользовательской документации](https://helpdesk.bitrix24.ru/) и [справочнику REST API](https://apidocs.bitrix24.ru/api-reference/) с учётом доменной зоны, тарифа, версии API и редакции коробочного продукта. Рекомендации архитектора в этом документе не являются гарантией наличия функции на конкретном портале.

> **Безопасность:** примеры предполагают только обезличенные или синтетические данные. Пароли, токены, URL действующих вебхуков, персональные данные и клиентские выгрузки хранить в Git запрещено.

## 1. Общая архитектура CRM Bitrix24

### 1.1. Назначение

CRM Bitrix24 — операционный контур управления обращениями, клиентами, коммерческими возможностями и связанными действиями сотрудников. Целевая CRM-архитектура должна обеспечивать:

- единые правила регистрации и квалификации обращений;
- сохранение истории коммуникаций и контекста отношений;
- управляемое движение коммерческой возможности по стадиям;
- разграничение доступа к данным;
- автоматизацию повторяемых действий без циклов и дублей;
- измеримость конверсий, времени прохождения стадий и результата;
- интеграцию с мастер-системами без конкурирующего редактирования.

### 1.2. Основные сущности и связи

| Сущность | Архитектурная роль | Типовые связи |
|---|---|---|
| Лид | Неквалифицированное обращение, если применяется классический режим CRM | При конвертации пользователь выбирает создаваемые контакт, компанию и/или сделку; результат зависит от сценария, прав и настроек CRM |
| Сделка | Отдельная коммерческая возможность | Контакт, компания, товары, активности, счёт, предложение, смарт-процессы |
| Контакт | Физическое лицо | Компания, одна или несколько сделок, активности |
| Компания | Юридическое лицо или организация | Контакты, сделки, реквизиты, активности |
| Товар | Элемент каталога предложения | Товарные позиции сделки, предложения, счёта или заказа |
| Счёт | Требование оплаты в поддерживаемой модели CRM | Клиент, сделка, товары, оплата; реализация зависит от версии сущности |
| Предложение | Коммерческое предложение | Клиент, сделка, товары, документы |
| Активность | Исполнимое или зафиксированное взаимодействие | CRM-элемент, ответственный, сроки, результат |
| Смарт-процесс | Пользовательская сущность с собственным жизненным циклом | CRM-элементы, задачи, календарь, стадии, автоматизация |

Связь не заменяет мастерство данных. Для клиента, реквизитов, товаров, цен, заказов, счетов, оплат и статусов должна быть назначена одна мастер-система. Двустороннее редактирование допускается только при формализованных правилах конфликтов.

### 1.3. Архитектурный подход

Рекомендуемая последовательность проектирования:

1. Зафиксировать AS IS, владельцев процесса, данные, риски и ограничения.
2. Выделить бизнес-события, сущности и их жизненные циклы.
3. Назначить мастер-системы и ключи идентификации.
4. Спроектировать права и минимально необходимые поля.
5. Определить стадии и контрольные точки.
6. Только затем проектировать роботов, триггеры, бизнес-процессы и REST-интеграции.
7. Подготовить аналитику, тесты, пилот и откат до рабочего запуска.

### 1.4. Отличие от классических CRM

Bitrix24 объединяет CRM с задачами, коммуникациями, документами, телефонией, контакт-центром, автоматизацией и совместной работой. Это сокращает число внешних систем, но повышает риск смешивания разных жизненных циклов в одной сущности.

Архитектор не должен превращать сделку в универсальный контейнер для продаж, производства, поддержки и внутреннего согласования. Для самостоятельного процесса с отдельными стадиями, правами и аналитикой следует рассмотреть смарт-процесс или специализированную систему. Официальная точка входа по CRM — [Поддержка24](https://helpdesk.bitrix24.ru/).

## 2. CRM сущности

### 2.1. Лиды

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Регистрация неквалифицированного обращения до подтверждения клиента и коммерческого потенциала |
| Когда использовать | Большой поток обращений, отдельная функция квалификации, необходимость измерять качество источников и конверсию в клиентов |
| Когда не использовать | Все обращения заранее квалифицированы; менеджер сразу работает со сделкой; лид дублирует существующего клиента без отдельного процесса |
| Ключевые поля | Название, статус, источник, ответственный, контактные данные, потребность, согласие на обработку данных, причина дисквалификации |
| Связи | При конвертации пользователь выбирает контакт, компанию и/или сделку; до конвертации доступны активности и канал обращения. Официальная инструкция: [Как конвертировать лид](https://helpdesk.bitrix24.ru/open/23260824/) (проверено 2026-08-10) |
| Автоматизация | Нормализация канала, назначение ответственного, SLA первого контакта, контроль дублей, квалификационные задачи |
| Права | Разделять просмотр, изменение, экспорт и удаление; учитывать очередь квалификации и руководителя |
| REST API | Семейство `crm.lead.*`; точные методы, поля и scope проверять в [справочнике API](https://apidocs.bitrix24.ru/api-reference/) |
| Ограничения | Лид усложняет процесс и аналитику; повторная конвертация и интеграции могут создавать дубли без внешнего ID и правил поиска |

**Рекомендация архитектора:** заранее определить критерий квалификации и обязательную причину дисквалификации. Лид без формального выхода превращается в параллельную базу контактов.

### 2.2. Сделки

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Управление отдельной коммерческой возможностью с суммой, вероятностью, стадиями и ожидаемым результатом |
| Когда использовать | Есть предмет продажи, клиент, ответственный, прогнозируемый результат и жизненный цикл возможности |
| Когда не использовать | Для постоянного профиля клиента, обращения поддержки без продажи, внутренней задачи или единственного вечного объекта на компанию |
| Ключевые поля | Название, направление, стадия, клиент, сумма, валюта, источник, ответственный, даты, причина отказа, внешние ID |
| Связи | Контакт, компания, товары, активности, предложения, счета, документы и смарт-процессы |
| Автоматизация | Контроль обязательности по стадиям, задачи следующего шага, документы, уведомления, эскалации, фиксация причин проигрыша |
| Права | По ролям, отделам, направлениям, своим/своего отдела/всем; отдельно контролировать экспорт и удаление |
| REST API | Семейство `crm.deal.*`; товарные позиции и связанные объекты проверять по актуальному справочнику |
| Ограничения | Одна сделка не должна одновременно представлять независимые продажи; смена направления может влиять на стадии, роботов и аналитику |

**Рекомендация архитектора:** единица сделки — одна коммерческая возможность. Повторная продажа обычно создаёт новую сделку и связывается с тем же клиентом.

### 2.3. Контакты

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Мастер-представление физического лица в CRM |
| Когда использовать | Для покупателя B2C, представителя B2B-компании, партнёра или иного физического лица |
| Когда не использовать | Для юридического лица, сделки, подразделения или временного обращения без подтверждённой личности |
| Ключевые поля | ФИО, телефоны, email, должность, компания, предпочтения коммуникации, согласия, внешний ID |
| Связи | Компании, сделки, активности и связанные смарт-процессы |
| Автоматизация | Нормализация телефонов/email, контроль дублей, обогащение только из разрешённых источников, актуализация согласий |
| Права | Ограничивать экспорт и массовое изменение; учитывать персональные данные и цели обработки |
| REST API | Семейство `crm.contact.*` |
| Ограничения | Один человек может представлять несколько организаций; правила главной компании и множественных связей нужно определить заранее |

### 2.4. Компании

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Представление юридического лица или организации как клиента, партнёра или поставщика |
| Когда использовать | B2B-продажи, договорные реквизиты, несколько контактных лиц, история отношений на уровне организации |
| Когда не использовать | Для направления продаж, филиала без самостоятельной юридической роли или каждой сделки одного клиента |
| Ключевые поля | Название, тип, телефоны, email, реквизиты, ИНН/регистрационные данные, ответственный, внешний ID |
| Связи | Контакты, сделки, активности, реквизиты, предложения, счета и смарт-процессы |
| Автоматизация | Проверка дублей по устойчивым идентификаторам, синхронизация реквизитов из мастер-системы, контроль ответственного |
| Права | Сегментация по ролям и отделам; отдельный контроль реквизитов и экспорта |
| REST API | Семейство `crm.company.*`; реквизиты имеют отдельные методы CRM |
| Ограничения | Название компании не является надёжным ключом; холдинги, филиалы и несколько юрлиц требуют формальной модели связей |

### 2.5. Товары

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Нормализованный каталог продаваемых товаров и услуг, используемый в товарных позициях |
| Когда использовать | Нужны единая номенклатура, цены, количество, скидки, себестоимость или товарная аналитика |
| Когда не использовать | Для произвольных комментариев к сделке или дублирования полноценного ERP-каталога без правил синхронизации |
| Ключевые поля | Наименование, SKU/внешний ID, единица измерения, цена, валюта, НДС, активность, раздел каталога |
| Связи | Сделки, предложения, счета, заказы и складские объекты в зависимости от конфигурации |
| Автоматизация | Синхронизация из мастер-каталога, проверка цены и валюты, запрет бесконтрольного создания дублей |
| Права | Отделять управление каталогом и ценами от использования товаров менеджерами |
| REST API | Актуальные методы каталога и товарных позиций проверять в API; старые `crm.product.*` могут отличаться от современной модели `catalog.*` |
| Ограничения | Сложные цены, остатки и варианты товара требуют проверки возможностей каталога, тарифа и интеграции с учётной системой |

### 2.6. Счета

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Фиксация требования оплаты и состава расчёта в поддерживаемой модели Bitrix24 |
| Когда использовать | Процессу нужен отдельный объект счёта со статусом, суммой, клиентом и товарами |
| Когда не использовать | Если мастер-система счетов — 1С/ERP и CRM должна хранить только ссылку и статус; если достаточно документа без отдельного жизненного цикла |
| Ключевые поля | Номер, клиент, сумма, валюта, статус, даты выставления/оплаты, реквизиты, внешний ID |
| Связи | Сделка, контакт/компания, товары, документы, оплата |
| Автоматизация | Создание после контрольной точки, синхронизация статуса оплаты, уведомления и защита от повторного выставления |
| Права | Финансовые поля и операции ограничиваются ролями; удаление и изменение оплаченного счёта контролируются отдельно |
| REST API | Реализация счетов зависит от используемой версии сущности; могут применяться универсальные методы `crm.item.*` или legacy-методы. Проверять на целевом портале |
| Ограничения | Нельзя предполагать единую модель счетов для всех порталов; требуется определить мастер-систему оплаты и правила отмены |

### 2.7. Предложения

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Версионируемое коммерческое предложение клиенту с товарами, ценами и сроком действия |
| Когда использовать | Требуется отдельная стадия согласования предложения, несколько вариантов или формальный документ до счёта |
| Когда не использовать | Для внутреннего расчёта без отправки клиенту или когда предложение полностью формируется и хранится во внешней CPQ/ERP |
| Ключевые поля | Номер, клиент, сделка, статус, сумма, валюта, срок действия, товары, внешний ID |
| Связи | Сделка, контакт/компания, товары и документ |
| Автоматизация | Генерация документа, контроль срока, напоминание, фиксация принятия или отказа |
| Права | Разделить подготовку, согласование скидки и отправку клиенту |
| REST API | Семейство `crm.quote.*`; доступность полей и операций проверять по API и порталу |
| Ограничения | Нельзя подменять предложением историю всех переговоров; версии и согласование цены должны иметь явное правило |

### 2.8. Активности

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Планирование и фиксация звонков, встреч, писем и других взаимодействий в контексте CRM |
| Когда использовать | Есть конкретное действие, срок, ответственный и ожидаемый результат |
| Когда не использовать | Для сложной исполнимой работы с чек-листом и участниками — предпочтительнее задача; для хранения произвольной заметки без действия |
| Ключевые поля | Тип, тема, начало/окончание, ответственный, завершённость, результат, связи с CRM |
| Связи | Лид, сделка, контакт, компания и другие поддерживаемые CRM-элементы |
| Автоматизация | Создание следующего дела, контроль просрочки, SLA ответа, фиксация результата коммуникации |
| Права | Наследуются из контекста и полномочий пользователя; доступ к письмам и звонкам требует отдельной проверки |
| REST API | Семейство `crm.activity.*`; коммуникации и провайдеры активностей проверяются отдельно |
| Ограничения | Автоматическое создание дел без закрытия предыдущих формирует шум; результат должен быть пригоден для аналитики |

### 2.9. Смарт-процессы

| Аспект | Архитектурное описание |
|---|---|
| Назначение | Моделирование отдельной предметной сущности с карточкой, стадиями, правами и автоматизацией |
| Когда использовать | Процесс имеет самостоятельный жизненный цикл: объект, рекламация, договор, закупка, заказ или сервисное обращение |
| Когда не использовать | Достаточно стандартной CRM-сущности, задачи или поля; новая сущность создаётся только ради другого представления тех же данных |
| Ключевые поля | Определяются моделью: системный идентификатор, название, стадия, ответственный, связи, внешний ID и предметные атрибуты |
| Связи | CRM-элементы, задачи, календарь и другие поддерживаемые объекты |
| Автоматизация | Роботы, триггеры и бизнес-процессы — при наличии соответствующих опций и тарифа |
| Права | Проектируются отдельно по ролям и операциям; наследование нельзя предполагать без проверки |
| REST API | Универсальные методы `crm.type.*` и `crm.item.*`; `entityTypeId`, поля и доступность проверять на портале |
| Ограничения | Доступность зависит от тарифа и контекста; чрезмерное число процессов усложняет навигацию, права и аналитику |

Официальная инструкция по настройке: [Как создать смарт-процесс в CRM](https://helpdesk.bitrix24.ru/open/18913884/).

## 3. Жизненный цикл клиента

### 3.1. Целевая схема

```text
Лид → Квалификация → Сделка → Оплата → Повторные продажи → Поддержка
```

Это логическая схема, а не требование использовать лиды на каждом портале. В простой CRM квалифицированное обращение может сразу создавать контакт/компанию и сделку.

| Этап | Рекомендуемые стадии или состояния | Контрольная точка | Автоматизация |
|---|---|---|---|
| Лид | Новый → В обработке → Связались → Квалифицирован / Дисквалифицирован | Источник, контактные данные, ответственный, первый контакт | Назначение, SLA, проверка дублей, задача на контакт |
| Квалификация | Потребность подтверждена → Бюджет/полномочия/срок уточнены | Формальный критерий готовности к сделке | Проверка обязательных полей, конвертация, причина отказа |
| Сделка | Новая → Диагностика → Решение → Предложение → Согласование → Выиграна / Проиграна | Следующий шаг, сумма, клиент, вероятность и причина перехода | Задачи, документы, контроль простоя, эскалации |
| Оплата | Счёт подготовлен → Выставлен → Частично оплачен → Оплачен / Отменён | Внешний ID счёта и подтверждённый статус мастер-системы | Идемпотентная синхронизация, уведомления, запрет дублей |
| Повторные продажи | Потенциал → Новая возможность → Сделка | Согласие и основание контакта, актуальность клиента | Сегментация, новая сделка, напоминание без спама |
| Поддержка | Новое обращение → Диагностика → Решение → Подтверждение → Закрыто | SLA, владелец, результат и связь с клиентом/продажей | Очередь, эскалация, уведомления, закрывающий контроль |

### 3.2. Типовые ошибки жизненного цикла

- один статус «В работе» вместо измеримых стадий;
- стадия отражает действие сотрудника, но не состояние возможности;
- выигрыш сделки используется до подтверждения результата;
- оплата определяется ручным флагом при наличии мастер-системы;
- поддержка ведётся в той же продаже и искажает цикл сделки;
- повторная продажа перезаписывает старую сделку;
- нет причин дисквалификации и проигрыша;
- роботы двигают стадии циклически или без бизнес-события.

## 4. Проектирование CRM

### 4.1. Методика архитектора

До настройки необходимо определить:

| Область | Вопросы |
|---|---|
| Бизнес-модель | Что продаётся, кому, с какой периодичностью и что считается результатом |
| Отделы | Кто принимает обращения, продаёт, исполняет, поддерживает и контролирует |
| Роли | Кто создаёт, читает, изменяет, экспортирует и удаляет данные |
| Ответственность | Кто владелец процесса, данных, интеграции и каждой контрольной точки |
| Источники лидов | Каналы, UTM/метки, формы, телефония, почта, ручной ввод и партнёры |
| KPI | Конверсия, скорость реакции, длительность цикла, выручка, маржа, качество данных |
| Воронки | Независимые жизненные циклы, общие и разные стадии, правила передачи |
| Права | Модель свои/отдел/подотдел/все, специальные роли и ограничения экспорта |
| Интеграции | Мастер-системы, внешние ID, направление обмена, частота, ошибки и откат |

### 4.2. Чек-лист CRM-проектирования

- [ ] Уточнены Cloud/On-Premise, тариф или редакция, доменная зона и версия продукта.
- [ ] Зафиксированы AS IS, владельцы, пользователи и недопустимая остановка.
- [ ] Определено, используются ли лиды и по какому критерию квалифицируются.
- [ ] Для каждой сущности определены назначение, источник создания и жизненный цикл.
- [ ] Сделка соответствует одной коммерческой возможности.
- [ ] Контакт и компания не дублируют друг друга и другие системы.
- [ ] Назначена мастер-система для клиентов, реквизитов, товаров, цен, заказов, счетов и оплат.
- [ ] Определены устойчивые внешние ID и правила поиска дублей.
- [ ] Воронки разделены только при самостоятельных процессах.
- [ ] Каждая стадия имеет вход, выход, ответственного и измеримый смысл.
- [ ] Поля имеют владельца, тип, обязательность, права и места использования.
- [ ] Права проверены для рядового сотрудника, руководителя и администратора.
- [ ] Автоматизация не создаёт циклы и выдерживает повторный запуск.
- [ ] Интеграции имеют тайм-ауты, retry, идемпотентность, логирование и мониторинг.
- [ ] Аналитические показатели можно вычислить из фактически заполняемых данных.
- [ ] Подготовлены пилот, тестовые данные, позитивные и негативные сценарии.
- [ ] Есть план отката, журнал изменений и критерии готовности.

## 5. Поля CRM

### 5.1. Стандартные и пользовательские поля

Стандартное поле предпочтительно, если его семантика совпадает с задачей: оно лучше поддерживается интерфейсом, API, аналитикой и штатными интеграциями. Пользовательское поле создаётся только при отсутствии подходящего стандартного атрибута.

Для каждого пользовательского поля фиксируются:

- название и внутренний код;
- сущность и назначение;
- тип, множественность, формат, диапазон и точность;
- допустимые значения справочника;
- обязательность и стадия, на которой она включается;
- ответственный за заполнение и мастер-система;
- права просмотра и изменения;
- использование в карточках, фильтрах, роботах, БП, документах, REST, BI, импорте и экспорте;
- правила миграции и тестирования.

### 5.2. Выбор типа данных

| Данные | Предпочтительный тип | Ошибка |
|---|---|---|
| Дата события | Дата/дата-время | Строка с локальным форматом |
| Сумма | Деньги или число с определённой валютой | Текст «100 тыс.» |
| Закрытый перечень | Список | Свободный текст с вариантами написания |
| Да/нет | Булево | Список из нескольких неоднозначных значений |
| Ссылка на объект | Привязка к сущности | Хранение названия или ID в текстовом поле |
| Внешний идентификатор | Строка с форматом и уникальностью на уровне интеграции | Название компании как единственный ключ |
| Телефон/email | Стандартное коммуникационное поле | Дублирование в произвольной строке |

### 5.3. Именование и обязательность

Пользовательское название должно быть понятно сотруднику, а внутренний код — стабилен для интеграций. Код не следует менять после использования в REST, BI или автоматизациях. Рекомендуемый внутренний префикс проекта должен быть единым и документированным, например `UF_CRM_<DOMAIN>_<MEANING>`; реальный формат проверяется по сущности и способу создания.

Обязательность включается как можно позже, но до бизнес-события, для которого поле критично. Поле «обязательно всегда» часто блокирует импорт, интеграции и раннюю регистрацию обращения.

### 5.4. Лучшие практики

Создавать:

- поля, влияющие на маршрут, ответственность, документ, интеграцию или измеримый KPI;
- устойчивый внешний ID для идемпотентной интеграции;
- структурированные причины отказа с ограниченным справочником;
- поля согласий и правовых оснований, если это подтверждено требованиями.

Не создавать:

- дубль стандартного поля без формального обоснования;
- поле «на всякий случай» без владельца и потребителя;
- отдельное булево поле для каждого этапа вместо стадий или связанной сущности;
- свободный текст там, где требуется аналитика;
- поле с секретом, токеном или полным необезличенным payload;
- вычисляемые вручную показатели, если они выводятся из первичных данных.

Чтобы избежать перегрузки, разделяйте карточку по ролям и этапам, используйте обязательность по стадиям, регулярно измеряйте заполненность и удаляйте поле только после анализа всех зависимостей и согласованной миграции.

## 6. Воронки продаж

### 6.1. Базовая модель

Стандартная логическая воронка:

```text
Новая → Квалификация → Диагностика → Решение → Предложение → Согласование → Выиграна / Проиграна
```

Стадия должна отвечать на вопрос «в каком бизнес-состоянии находится возможность», а не «что сейчас делает менеджер». Для каждой стадии определяются входной критерий, обязательные данные, допустимый срок, ответственный, автоматизация и выходной критерий.

### 6.2. Несколько направлений

Отдельное направление оправдано, когда различаются как минимум несколько характеристик: жизненный цикл, роли, права, обязательные поля, автоматизация, SLA, финансовая модель или аналитика. Разница только в продукте или источнике обычно решается полем, товаром или сегментом.

### 6.3. Примеры архитектур

| Модель | Пример стадий | Архитектурный комментарий |
|---|---|---|
| B2B | Новая → Discovery → Техническое решение → КП → Закупка/юристы → Договор → Выиграна | Контакт и компания обязательны; учитывать несколько участников, реквизиты, длинный цикл и версии КП |
| B2C | Новая → Связались → Потребность → Предложение → Оплата → Выиграна | Короткий цикл; приоритет скорости ответа, дедупликации контактов и каналов коммуникации |
| EdTech | Заявка → Консультация → Подбор программы → Договор/оферта → Оплата → Зачислен | Обучающий цикл после продажи лучше отделить в смарт-процесс; учитывать плательщика и обучающегося |
| Услуги | Запрос → Бриф → Оценка → КП → Согласование → Договор → Оплата | Исполнение проекта не следует моделировать бесконечным продолжением сделки; использовать задачи или отдельный процесс |
| Сложная продажа | Discovery → Пресейл → Пилот → Комитет → Закупка → Контракт | Нужны роли участников, контрольные документы, вероятности и причины остановки; автоматизация не заменяет governance |

## 7. Автоматизация CRM

Официальная база: [Роботы и триггеры в Bitrix24](https://helpdesk.bitrix24.ru/open/24633726/) и [документация REST API](https://apidocs.bitrix24.ru/).

### 7.1. Выбор механизма

| Механизм | Использовать для | Контроль архитектора |
|---|---|---|
| Робот | Действие при попадании элемента на стадию или по времени | Условия, повторный запуск, исполнитель, ошибка, влияние на стадию |
| Триггер | Реакция на подтверждённое событие и возможный переход стадии | Источник события, защита от повторов и нежелательного обратного перехода |
| Бизнес-процесс | Многошаговое согласование, ветвление, роли и длительный процесс | Состояние экземпляра, тайм-аут, отмена, эскалация и версия шаблона |
| REST-интеграция | Обмен с внешней системой или логика вне штатных возможностей | Авторизация, лимиты, retry, идемпотентность, журнал и мониторинг |
| Задача | Исполнимая работа с результатом, сроком и ответственным | Не создавать дубли; закрытие должно быть частью контрольной точки |
| Уведомление | Информирование о событии или отклонении | Адресат, полезность, частота и отсутствие чувствительных данных |

### 7.2. Cloud Bitrix24

**Подтверждённый архитектурный контекст:** нет доступа к ядру, серверному PHP-коду и базе данных; применяются штатные настройки, роботы, триггеры, бизнес-процессы, приложения и REST API в пределах тарифа и доступных прав.

**Рекомендации:**

- сначала использовать штатные настройки;
- проверять доступность действия на конкретном тарифе;
- считать REST-вызовы повторяемыми и ограниченными по интенсивности;
- не строить критический процесс на единственном уведомлении;
- тестировать на отдельной воронке или тестовом портале.

### 7.3. Коробочная версия

Дополнительно учитываются версия продукта и модулей, PHP, cron/агенты, очереди, база данных, файловые права, веб-сервер, резервное копирование, обновления и нагрузка. Изменение ядра запрещено; используются расширяемые механизмы и отдельные модули. Официальная точка входа: [документация коробочного Bitrix24](https://dev.1c-bitrix.ru/docs/portal.php).

Перед доработкой требуются стенд, совместимая копия конфигурации, резервная копия, план обновления и измерение нагрузки.

## 8. Права доступа

### 8.1. Принципы

- минимально необходимые права;
- роли задаются по функциям, а не по фамилиям;
- организационная структура не всегда равна структуре доступа;
- просмотр, изменение, удаление и экспорт оцениваются отдельно;
- руководитель получает доступ в пределах управленческой ответственности;
- интеграционные пользователи имеют отдельную учётную запись и минимальные scope;
- администратор не используется как штатная роль менеджера.

### 8.2. Типовая матрица

Матрица является рекомендацией и адаптируется после проверки доступных настроек портала.

| Роль | Лиды/сделки | Контакты/компании | Каталог/цены | Экспорт | Удаление | Настройки/автоматизация |
|---|---|---|---|---|---|---|
| Менеджер | Свои: просмотр и изменение | Связанные/свои | Использование без управления | Нет | Нет или строго ограничено | Нет |
| Руководитель группы | Свои и отдела | В пределах отдела | Просмотр | По согласованию | Ограничено | Просмотр аналитики |
| РОП | Все в направлении | Все в направлении | Просмотр, согласование скидок | Ограниченный | По регламенту | Управление процессом без системного администрирования |
| Финансы | Счета, суммы и оплаты по функции | Реквизиты по функции | Цены по функции | Финансовый по регламенту | Нет | Нет |
| Контроль качества | Чтение и активности | Ограниченное чтение | Нет | Нет | Нет | Нет |
| Интеграция | Только нужные сущности и операции | Только по контракту | Только по контракту | API по контракту | Запрещено без отдельного сценария | Нет |
| CRM-администратор | По регламенту сопровождения | По регламенту | Настройка при необходимости | Только для работ | Только с согласованием | Да |

Проверка прав выполняется тестовыми пользователями каждой роли, включая прямой URL, поиск, фильтры, мобильное приложение, экспорт, REST и связанные сущности.

## 9. Аналитика CRM

### 9.1. Набор показателей

| Показатель | Определение и условие достоверности |
|---|---|
| Количество новых обращений | Единое правило даты и источника; дубли контролируются |
| Скорость первого ответа | Есть точное событие поступления и подтверждённая первая коммуникация |
| Конверсия лида | Формально определены квалифицированный и дисквалифицированный исход |
| Конверсия сделки | Единое окно анализа и причины закрытия |
| Длительность цикла | Корректные даты входа/выхода стадий, без массовых ручных переносов |
| Время на стадии | Стадии имеют стабильную семантику и не используются циклически |
| Выручка | Понятно, используется сумма сделки, счёта или подтверждённая оплата |
| Эффективность менеджера | Учитываются входящий поток, сегмент, качество данных и командная модель |
| Активности и SLA | Дела создаются и закрываются единообразно, результат фиксируется |
| Причины отказа | Справочник ограничен, обязателен и регулярно нормализуется |

### 9.2. BI

BI применяется, когда штатных отчётов недостаточно для объединения наборов данных, сложных расчётов или управленческих срезов. До построения BI проверяются мастер-источник суммы, валюта, часовой пояс, стадии, архив, дубли и качество обязательных полей. Официальный обзор: [BI Конструктор: наборы данных](https://helpdesk.bitrix24.ru/open/24355590/).

Отчёт не исправляет плохие данные. При неполной истории или изменённой семантике стадий ограничение достоверности должно быть указано рядом с показателем.

## 10. Интеграции

| Интеграция | Архитектурная задача | Основные риски и контроль |
|---|---|---|
| Сайт и CRM-формы | Создание обращения с источником, согласием и контекстом | Спам, дубли, потеря UTM, неверный ответственный; валидация и тест каждой формы |
| Телефония | Связать звонок, запись и результат с клиентом и ответственным | Дубли номеров, права на записи, маршрутизация, регион и тариф; см. [официальную инструкцию](https://helpdesk.bitrix24.ru/open/6450911/) |
| Мессенджеры и открытые линии | Единая очередь коммуникаций и создание CRM-элементов | Повторное создание, потеря диалога, персональные данные, SLA и смена ответственного |
| 1С/ERP | Клиенты, реквизиты, каталог, заказ, счёт, оплата и статусы | Конфликт мастер-систем, разные ID, частичные ошибки, валюты и удаление; нужна карта обмена |
| Внешние API | Дополнительный канал или бизнес-сервис | Авторизация, лимиты, тайм-ауты, retry, идемпотентность, мониторинг и договорённость о schema evolution |

Для каждой интеграции фиксируются направление обмена, событие запуска, mapping, внешний ID, ключ дубля, SLA, batch, retry, dead-letter/отчёт ошибок, права, персональные данные и процедура повторного запуска. Актуальные методы проверяются только по [официальному REST API](https://apidocs.bitrix24.ru/api-reference/). Перед собственной разработкой оценивается [официальный Маркетплейс](https://www.bitrix24.ru/apps/).

## 11. Cloud vs On-Premise

| Возможность | Облако | Коробка | Комментарий архитектора |
|---|---|---|---|
| Управление инфраструктурой | На стороне Bitrix24 | На стороне владельца | В коробке обязательны эксплуатационная модель и ответственные |
| Доступ к ядру и БД | Нет | Технически возможен | Ядро не изменять; прямую запись в БД не использовать как штатную интеграцию |
| Обновления | Управляются поставщиком | Планируются владельцем | Для коробки нужен стенд, backup и проверка совместимости |
| Штатные CRM-настройки | Доступны в пределах тарифа | Доступны в пределах редакции и версии | Наличие функции проверять на целевом портале |
| Роботы и бизнес-процессы | В пределах тарифа | В пределах редакции/модулей | Проверять доступность конкретного действия и права |
| REST API | Основной механизм расширения | Доступен, зависит от версии модулей | Контракты и лимиты проверять; не предполагать полную идентичность версий |
| Серверный PHP и модули | Недоступны | Возможны отдельные модули | Использовать расширяемые механизмы, не модифицировать ядро |
| Cron, очереди, агенты | Не управляются клиентом | Требуют эксплуатации | Мониторинг фоновых задач входит в архитектуру коробки |
| Масштабирование | Управляется сервисом в рамках продукта | Ответственность владельца | Нужны нагрузочные оценки, БД, кеш, веб-кластер при необходимости |
| Резервное копирование | По возможностям сервиса и доступным экспортам | Полная политика владельца | Перед изменениями фиксировать доступный способ восстановления |
| Логи и диагностика | Ограничены интерфейсом и интеграцией | Шире, включая серверные журналы | В обоих случаях исключать секреты и лишние персональные данные |
| Кастомный UI | Виджеты и приложения в разрешённых точках | Дополнительно расширения коробки | Стоимость сопровождения и обновлений должна быть обоснована |
| Доменная зона и регуляторика | Зависит от зоны сервиса | Зависит от размещения владельца | Проверять хранение данных, телефонию и доступные интеграции |
| Скорость внедрения | Обычно выше штатными средствами | Зависит от инфраструктуры и доработок | Не выбирать коробку только ради одной локальной модификации |

## 12. Типовые ошибки внедрения

| № | Ошибка | Последствие | Профилактика |
|---:|---|---|---|
| 1 | Слишком много полей | Низкая заполняемость и сопротивление пользователей | Создавать поле только с владельцем и потребителем |
| 2 | Дублирование стандартных полей | Расхождение данных и сложная интеграция | Сначала проверять стандартную модель |
| 3 | Неправильная структура стадий | Некорректная конверсия и непонятный процесс | Определять вход/выход и бизнес-смысл стадии |
| 4 | Стадии названы действиями менеджера | Состояние сделки не измеряется | Отделять состояние от задачи |
| 5 | Отсутствие ролей | Избыточный доступ и неконтролируемые изменения | Спроектировать матрицу до запуска |
| 6 | Автоматизация плохого процесса | Ошибки масштабируются быстрее | Стабилизировать ручной процесс и контрольные точки |
| 7 | Смешивание лидов и сделок | Дубли и двойная аналитика | Формально определить критерий квалификации |
| 8 | Одна сделка на все продажи клиента | Потеря истории возможностей | Новая сделка на отдельную продажу |
| 9 | Отдельная компания для каждого направления | Фрагментация клиента | Одна компания без подтверждённого юридического разделения |
| 10 | Название компании как ключ | Ошибочные слияния и дубли | Использовать устойчивый внешний ID и реквизиты |
| 11 | Нет мастер-системы | Конфликты при двусторонней синхронизации | Назначить владельца каждого типа данных |
| 12 | Нет защиты от повторов | Дубли сделок, задач и счетов | Идемпотентность, внешний ID и журнал операций |
| 13 | Бесконтрольные retry | Шторм запросов и повторные изменения | Ограниченный backoff и классификация ошибок |
| 14 | Нет dry-run у массовой операции | Риск необратимого изменения | Предпросмотр, лимит выборки и отчёт |
| 15 | Роботы создают циклы стадий | Бесконечные запуски и шум | Карта событий, флаги повторов и негативный тест |
| 16 | Автоматические задачи без дедупликации | Перегрузка сотрудников | Проверка открытой задачи и ключ сценария |
| 17 | Нет причин отказа | Невозможно улучшать процесс | Ограниченный обязательный справочник |
| 18 | Нет аналитики до запуска | Нужные данные не собираются | Проектировать KPI вместе с полями и стадиями |
| 19 | KPI без проверки качества данных | Ложные управленческие выводы | Контроль полноты, дублей и семантики |
| 20 | Избыточные направления сделок | Сложная поддержка и раздробленная аналитика | Создавать направление только для отдельного цикла |
| 21 | Поддержка ведётся в сделках продаж | Искажение цикла и ответственности | Выделить задачу или смарт-процесс |
| 22 | Реальные данные в тестах | Утечка и регуляторный риск | Только синтетические и обезличенные фикстуры |
| 23 | Секреты в коде и логах | Компрометация портала | `.env`, секрет-хранилище и маскирование |
| 24 | Тестирование на рабочем клиенте | Потеря данных и простой | Тестовый портал/воронка и пилот |
| 25 | Нет плана отката | Невозможно безопасно восстановить процесс | Backup, карта изменений и критерий остановки |
| 26 | Игнорирование тарифа или версии | Решение недоступно после проектирования | Проверять на целевом портале до согласования |
| 27 | Права проверены только администратором | Пользователи не видят нужное или видят лишнее | Тестовые пользователи каждой роли |
| 28 | Массовое удаление вместо архивирования | Потеря истории и аналитики | Согласование, экспорт, архив и тестовая выборка |

## 13. Чек-лист аудитора CRM

### 13.1. Контекст и безопасность

- [ ] Определены Cloud/On-Premise, доменная зона, тариф/редакция и версия.
- [ ] Зафиксированы права аудитора и ограничения доступа.
- [ ] Согласованы объём, период, сущности и недопустимые действия.
- [ ] Экспорт и копирование персональных данных не выполняются без основания.
- [ ] Есть тестовый портал/воронка или установлен режим read-only.

### 13.2. Структура CRM

- [ ] Установлен режим работы с лидами и критерий квалификации.
- [ ] Каждая сделка представляет отдельную возможность.
- [ ] Направления соответствуют самостоятельным жизненным циклам.
- [ ] Контакты, компании и смарт-процессы имеют определённое назначение.
- [ ] Нет сущностей, используемых как универсальное хранилище.

### 13.3. Поля и данные

- [ ] Составлен реестр стандартных и пользовательских полей.
- [ ] У каждого поля есть владелец, источник, тип и потребитель.
- [ ] Проверены заполненность, уникальность, справочники и устаревшие поля.
- [ ] Найдены дубли телефонов, email, компаний и внешних ID.
- [ ] Проверены форматы дат, валют, сумм, реквизитов и часовой пояс.
- [ ] Поля проверены в роботах, БП, документах, REST, BI, импорте и экспорте.

### 13.4. Воронки и жизненный цикл

- [ ] Для стадий определены вход, выход, SLA и ответственный.
- [ ] Проверены активные элементы на устаревших стадиях.
- [ ] Причины отказа обязательны, нормализованы и анализируются.
- [ ] Победа, оплата и исполнение не смешаны без обоснования.
- [ ] Проверены туннели, повторные переходы и история изменений.

### 13.5. Права

- [ ] Есть актуальная ролевая матрица.
- [ ] Проверены свои/отдел/подотдел/все для основных операций.
- [ ] Отдельно проверены экспорт, удаление, финансы и настройки.
- [ ] Проверены мобильный интерфейс, поиск, прямые ссылки и связанные сущности.
- [ ] Интеграционные пользователи имеют минимальные права.

### 13.6. Автоматизация

- [ ] Составлен реестр роботов, триггеров и бизнес-процессов.
- [ ] Для каждого зафиксированы запуск, условия, действие и исполнитель.
- [ ] Проверены циклы, дубли, повторный запуск, тайм-ауты и эскалации.
- [ ] Нет задач и уведомлений без владельца или полезного результата.
- [ ] Ошибки видимы, журналируются и имеют процедуру восстановления.

### 13.7. Интеграции

- [ ] Составлена карта интеграций и мастер-систем.
- [ ] Проверены внешние ID, mapping и направление обмена.
- [ ] Проверены лимиты, pagination, batch, timeout, retry и идемпотентность.
- [ ] Секреты не находятся в коде, полях CRM и логах.
- [ ] Есть мониторинг, отчёт частичных ошибок и повторный запуск.

### 13.8. Аналитика и результат аудита

- [ ] Определения KPI согласованы с владельцами процесса.
- [ ] Конверсия, длительность стадий и суммы основаны на качественных данных.
- [ ] Проверены архив, дубли, валюты и массовые изменения.
- [ ] Ограничения достоверности явно описаны.
- [ ] Результат содержит факты, риски, приоритет, решение, тест и откат.
- [ ] Подготовлены краткосрочный план исправлений и целевая архитектура.
