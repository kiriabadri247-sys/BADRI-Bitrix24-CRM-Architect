# Bitrix24 Testing Engineering Knowledge Base

Инженерная база знаний для планирования, выполнения и аудита тестирования решений Bitrix24. Документ рассчитан на Senior QA Engineer, Test Lead, CRM Quality Auditor и Senior Bitrix24 Solution Architect.

> **Статус сведений:** продуктовые факты основаны только на официальных источниках из `knowledge/SOURCES.md`. Названия настроек, доступность функций, лимиты, состав журналов и поведение конкретного портала зависят от тарифа, редакции, версии, модулей и прав и поэтому проверяются на целевом окружении. «Рекомендация архитектора» означает инженерную практику, а не обещание функции Bitrix24.

> **Безопасность:** тесты выполняются на отдельном контуре или изолированной тестовой области с синтетическими данными. Нагрузочные, разрушающие, массовые и security-проверки production запрещены без письменного согласования, резервной копии, плана отката и окна работ.

## 1. Архитектура тестирования Bitrix24

Тестовая архитектура связывает требование, настройку, данные, роль, интеграцию, ожидаемый результат и доказательство. Единицей контроля является не экран, а бизнес-сценарий от источника события до наблюдаемого результата.

```text
Requirement -> Risk -> Test case -> Test data -> Execution
      |                                      |
      +-> Configuration baseline             +-> Evidence -> Defect -> Retest
```

| Слой | Что проверяется | Артефакт | Критерий выхода |
|---|---|---|---|
| Business | Процесс, роли, SLA, исключения | UAT scenarios | Владелец принял результат |
| Application | CRM, Smart Processes, задачи, BI | Functional suite | Acceptance criteria выполнены |
| Automation | Роботы, триггеры, БП | Transition matrix | Нет циклов и пропущенных ветвей |
| Integration | REST, webhooks, телефония, 1С | Contract tests | Повторы и ошибки контролируются |
| Data | Поля, связи, миграция, качество | Reconciliation report | Баланс и выборка совпали |
| Access | Роли и области видимости | Permission matrix | Позитивные и негативные тесты пройдены |
| Platform | Cloud либо On-Premise | Environment passport | Версия и ограничения зафиксированы |

**Рекомендация архитектора:** применять risk-based testing. Максимальный приоритет получают потеря или раскрытие данных, неверные деньги, дубли, блокировка процесса, ошибочные права и необратимые массовые действия.

## 2. Виды тестирования

| Вид | Цель | Когда | Ограничение |
|---|---|---|---|
| Smoke | Подтвердить жизнеспособность сборки | После изменения или релиза | Не заменяет полную проверку |
| Functional | Проверить требования | На каждой функции | Нужна трассируемость |
| Regression | Найти побочные эффекты | Перед релизом | Набор зависит от impact analysis |
| UAT | Получить бизнес-приёмку | До production | Выполняет уполномоченный бизнес |
| Integration | Проверить границы систем | При изменении контракта | Нужны fault scenarios |
| Security | Проверить контроль доступа и секретов | До запуска и периодически | Только в согласованных границах |
| Performance | Оценить время и устойчивость | По профилю нагрузки | Не запускать бесконтрольно в Cloud |
| Migration | Сверить перенос | На rehearsal и cutover | Нужны rollback и reconciliation |

## 3. Smoke Testing

Smoke suite короткий, детерминированный и блокирует дальнейшее тестирование при критическом отказе.

- [ ] пользователь с тестовой ролью входит и видит разрешённую рабочую область;
- [ ] создаётся основная CRM-сущность с минимально допустимыми полями;
- [ ] сущность проходит один ключевой переход;
- [ ] обязательная автоматизация запускается один раз;
- [ ] задача или уведомление получает правильного адресата;
- [ ] критичная интеграция отвечает безопасным тестовым запросом;
- [ ] запрещённое действие действительно запрещено;
- [ ] след операции доступен в предусмотренной истории или журнале.

**Ошибка:** считать успешное открытие портала достаточным smoke test.

## 4. Functional Testing

Для каждого требования проверяются happy path, альтернативная ветвь, отказ, повторный запуск и права.

| Поле test case | Содержание |
|---|---|
| ID / Requirement | Устойчивые идентификаторы |
| Preconditions | Роль, сущность, стадия, конфигурация |
| Data | Только синтетический набор |
| Steps | Однозначные действия |
| Expected | Данные, состояние, история и side effects |
| Actual / Evidence | Факт, время, скриншот или безопасный лог |

## 5. Regression Testing

Regression suite формируется по карте зависимостей: поле влияет на карточку, обязательность, фильтры, роботов, БП, REST, импорт, документы и BI; стадия — на права, автоматизацию, туннели, аналитику и активные элементы.

```text
Changed object -> Dependencies -> Risk score -> Selected regression
     -> Execute -> Compare baseline -> Release decision
```

**Рекомендация архитектора:** иметь уровни `R0` (smoke), `R1` (critical journey), `R2` (domain), `R3` (full). Состав и владелец каждого уровня фиксируются.

## 6. UAT

UAT подтверждает пригодность решения бизнесу, но не переносит ответственность за техническое качество на пользователя.

- [ ] согласованы участники и полномочия подписанта;
- [ ] сценарии написаны языком результата бизнеса;
- [ ] данные синтетические, но реалистичные;
- [ ] известные ограничения перечислены до начала;
- [ ] каждый критерий имеет статус и доказательство;
- [ ] замечания классифицированы как defect, change request или обучение;
- [ ] есть формальная запись решения о приёмке.

## 7. Integration Testing

| Контроль | Позитивный кейс | Негативный кейс |
|---|---|---|
| Contract | Валидный payload принят | Неизвестное поле/тип обработаны |
| Identity | External ID сопоставлен | Дубликат и конфликт ключа |
| Timing | Ответ в согласованное время | Timeout, задержка, out-of-order |
| Reliability | Одно событие — один эффект | Повтор не создаёт дубль |
| Recovery | После сбоя обмен продолжен | Partial result согласован |
| Security | Минимальный scope | Отозванный секрет отклонён |

Нельзя считать HTTP `200` доказательством бизнес-успеха без проверки тела ответа и итогового состояния.

## 8. REST API Testing

Точный контракт метода проверяется в [официальном REST API reference](https://apidocs.bitrix24.ru/api-reference/).

- авторизация и минимальные права;
- обязательные, опциональные и read-only поля;
- типы, кодировка, даты, валюты и множественные значения;
- фильтрация, сортировка, пагинация и минимальный `select`;
- HTTP-ошибка и ошибка в API payload;
- timeout, ограниченный retry и идемпотентность;
- batch: результат каждой команды и частичный отказ;
- отзыв доступа и отсутствие секретов в логах.

```text
Client -> Validator -> REST method -> Response validator -> State verification
                 \-> retry policy       \-> safe evidence
```

## 9. Webhook Testing

Входящий webhook проверяется как секретный REST endpoint, исходящий — как недоверенное событие до валидации. Детали подтверждаются в [официальной документации REST](https://apidocs.bitrix24.ru/).

| Проверка | Входящий | Исходящий |
|---|---|---|
| Авторизация | Разрешённый и отозванный URL | Поддерживаемая проверка источника |
| Повтор | Идемпотентный запрос | Duplicate delivery без дубля эффекта |
| Ошибка | API error распознан | Endpoint отвечает ошибкой/timeout |
| Данные | Нет секрета в evidence | Payload валидируется до обработки |
| Отзыв | Старый URL перестал работать | Подписка отключена по регламенту |

Не предполагать подпись, retry policy или гарантированный порядок событий без официального контракта.

## 10. CRM Testing

Проверяются лиды, сделки, контакты, компании, товарные позиции, активности и связи в используемой модели.

- [ ] критерий создания сущности подтверждён;
- [ ] обязательность полей работает на нужной стадии;
- [ ] стадии и причины отказа непротиворечивы;
- [ ] повторное обращение не создаёт необоснованный дубль;
- [ ] ответственный и наблюдатели назначаются корректно;
- [ ] связи клиент—сделка—активность сохранены;
- [ ] удаление, экспорт и массовые действия ограничены;
- [ ] аналитические даты и суммы формируются корректно.

## 11. Smart Process Testing

Для каждого `entityTypeId` проверяются доступные операции `crm.item.*`, поля, категории, стадии, связи, права и автоматизация. Конкретные возможности сверяются с [официальной статьёй о смарт-процессах](https://helpdesk.bitrix24.ru/open/18913884/) и API reference.

| Область | Проверка | Риск |
|---|---|---|
| Type | Верный `entityTypeId` | Работа не с тем типом |
| Category | Изоляция направлений | Пересечение стадий и прав |
| Stage | Допустимые переходы | Обход контроля |
| Relation | Обе стороны связи | Висячая ссылка |
| Field | Тип и обязательность | Потеря или искажение данных |

## 12. Business Process Testing

```text
Start -> Preconditions -> Branch -> Activity -> Wait/Approval -> Result
  |          |             |          |              |
manual/auto  invalid       each path  error/retry     timeout/delegate
```

Тестируются ручной и доступный автоматический запуск, условия, параллельные ветви, ожидания, согласования, делегирование, исключения, повторный запуск и завершение. Точный набор активностей зависит от портала.

## 13. Robot Testing

| Сценарий | Ожидание |
|---|---|
| Первый вход на стадию | Робот выполняется согласно настройке |
| Повторный вход | Нет незапланированного повторного эффекта |
| Условие ложно | Действие не выполняется |
| Поле отсутствует | Контролируемая ошибка или ветвь |
| Нет прав | Нет скрытого успеха |
| Одновременное событие | Нет цикла и гонки |

## 14. Permissions Testing

Тестировать нужно отдельными тестовыми пользователями, а не через администратора. Матрица покрывает create/read/update/delete/export, стадии, направления, поля, коммуникации, файлы, аналитику и настройки.

- [ ] разрешённое действие проходит;
- [ ] запрещённое действие блокируется через UI;
- [ ] то же действие блокируется через REST;
- [ ] прямой URL не раскрывает объект;
- [ ] поиск, фильтр, экспорт и BI не обходят ограничение;
- [ ] смена отдела, роли и ответственного пересчитывает доступ ожидаемо;
- [ ] автоматизация не расширяет доступ несанкционированно.

## 15. Performance Testing

Нагрузочный профиль включает объём, concurrency, частоту событий, размер сущности и допустимый percentile latency. В Cloud нельзя управлять инфраструктурой или проводить неконтролируемый stress test; используются согласованные безопасные нагрузки и опубликованные ограничения. В On-Premise дополнительно контролируются web/PHP, БД, файловая система, агенты/cron и очереди.

| Тест | Цель | Stop condition |
|---|---|---|
| Baseline | Нормальная задержка | Нестабильное окружение |
| Load | Ожидаемый профиль | Ошибки/влияние на пользователей |
| Spike | Краткий пик | Риск деградации production |
| Soak | Утечки и накопление очереди | Исчерпание ресурса |
| Recovery | Возврат после сбоя | Потеря данных |

## 16. Security Testing

Security testing проводится только в согласованном scope. Проверяются least privilege, секреты, отзыв доступа, экспорт, логи, входные данные, доступ по прямой ссылке и изоляция сред. Запрещены destructive exploitation и сканирование production без разрешения.

```text
Identity -> Authentication -> Authorization -> Data -> Audit
                  |               |
              session/revoke   UI + API + export
```

## 17. BI Testing

Доступность BI Конструктора и наборов данных зависит от тарифа и конфигурации; официальная отправная точка — [наборы данных BI](https://helpdesk.bitrix24.ru/open/24355590/).

- сверить grain, dimensions, measures и временную зону;
- сверить row count и контрольную сумму на выборке;
- проверить валюту, округление, закрытые стадии и отмены;
- проверить фильтры, права и обезличивание;
- сравнить dashboard с мастер-источником;
- проверить refresh и поздние изменения;
- не объявлять расхождение дефектом до согласования формулы.

## 18. Migration Testing

```text
Profile source -> Mapping -> Dry-run -> Test import -> Reconciliation
       -> Fix rules -> Rehearsal -> Cutover -> Post-check -> Rollback window
```

| Контроль | Метрика |
|---|---|
| Полнота | Source count = created + updated + skipped + failed |
| Точность | Поля и связи совпали на выборке |
| Уникальность | Дубли до/после по согласованным ключам |
| Referential integrity | Нет потерянных связей |
| Repeatability | Повтор не создаёт дубль |
| Auditability | Каждая строка имеет итог без ПДн в логе |

## 19. Negative Testing

Проверяются пустые и неверные значения, отсутствие прав, закрытая стадия, удалённая связь, timeout, duplicate event, out-of-order, истёкший или отозванный доступ, partial batch, недоступный провайдер и превышение согласованных границ.

**Правило:** ожидаемый результат негативного теста — не только ошибка, но и отсутствие нежелательного side effect.

## 20. Edge Cases

| Граница | Пример синтетического кейса |
|---|---|
| Пустота | `null`, пустая строка, отсутствующее поле |
| Размер | 0, 1, допустимый максимум, максимум+1 |
| Время | граница суток, месяца, года, часовой пояс |
| Текст | Unicode, пробелы, переносы, спецсимволы |
| Деньги | 0, отрицательное, округление, другая валюта |
| Identity | дубль телефона/email, смена external ID |
| Concurrency | два изменения одного объекта |
| Lifecycle | удалённый/закрытый/перенесённый объект |

## 21. Test Data

Паспорт набора фиксирует владельца, назначение, генератор, объём, срок хранения и способ очистки. Реальные персональные, финансовые и клиентские данные запрещены.

- [ ] данные воспроизводимы;
- [ ] роли и связи реалистичны;
- [ ] набор содержит positive, negative и boundary cases;
- [ ] идентификаторы не совпадают с production;
- [ ] секреты заменены безопасными заглушками;
- [ ] очистка не затрагивает чужие сущности.

## 22. Synthetic Data

Использовать домены `example.test`, номера вида `+00000000000`, вымышленные имена и префикс `QA-<run-id>`. Нельзя маскировать реальные данные слабой заменой нескольких символов: обратимо обезличенный набор остаётся чувствительным.

| Тип | Безопасный пример | Запрещено |
|---|---|---|
| Email | `qa-001@example.test` | Реальный mailbox |
| Телефон | `+00000000000` | Номер клиента |
| Компания | `QA Synthetic LLC` | Название заказчика |
| ID | `EXT-QA-0001` | Production external ID |
| Secret | `<WEBHOOK_URL>` | Действующий URL |

## 23. Test Environment

Environment passport содержит Cloud/On-Premise, тариф/редакцию, версию, модули, дату baseline, роли, интеграции, ограничения и владельца.

- [ ] конфигурация сопоставима с production;
- [ ] доступ ограничен;
- [ ] интеграции направлены на sandbox endpoints;
- [ ] уведомления и телефония не уходят реальным адресатам;
- [ ] есть reset/restore procedure;
- [ ] drift контролируется;
- [ ] доказательства не содержат секретов и ПДн.

## 24. Sandbox

Sandbox — архитектурное требование к изоляции, а не гарантия отдельной штатной функции на любом тарифе. В Cloud доступность тестового портала или безопасной тестовой области проверяется отдельно. В On-Premise возможен отдельный стенд, но копирование production требует правового основания, обезличивания и защиты.

```text
Production config --approved export/no data--> Test baseline
Synthetic generator -------------------------> Test data
Sandbox integrations <-----------------------> External sandboxes
```

## 25. Acceptance Criteria

Критерий должен быть конкретным, наблюдаемым и проверяемым.

| Плохо | Хорошо |
|---|---|
| CRM работает быстро | P95 для согласованного сценария укладывается в согласованный порог |
| Права настроены | Матрица ролей пройдена positive/negative тестами |
| Дубли отсутствуют | Повтор события с тем же ключом не создаёт вторую сущность |
| Отчёт правильный | Формула, период, grain и контрольная выборка совпадают |

## 26. Bug Lifecycle

```text
New -> Triage -> Assigned -> In progress -> Ready for retest
 -> Retest -> Closed
             \-> Reopened
New -> Duplicate / Not a defect / Deferred (with rationale)
```

Defect содержит environment, build/baseline, preconditions, steps, expected, actual, evidence, severity, affected data и workaround. Change request не маскируется под defect.

## 27. Severity vs Priority

| Severity | Воздействие | Типичный пример | Priority |
|---|---|---|---|
| Critical | Потеря/раскрытие данных, остановка ключевого процесса | Чужие CRM-данные доступны роли | Обычно немедленно |
| High | Ключевой сценарий не работает, обхода нет | Сделка не проходит обязательный этап | Высокий |
| Medium | Ограниченный эффект, есть обход | Некорректное уведомление | По релизному риску |
| Low | Косметика/удобство | Текстовая неточность | Может быть отложен |

Severity описывает ущерб, priority — порядок исправления. Решение принимает triage-команда по риску и срокам.

## 28. Release Checklist

- [ ] scope и список изменений заморожены;
- [ ] impact analysis и regression scope согласованы;
- [ ] smoke, critical journey и security checks пройдены;
- [ ] UAT подписан уполномоченным владельцем;
- [ ] открытые дефекты и ограничения приняты;
- [ ] backup/export и rollback готовы;
- [ ] миграция прошла rehearsal и reconciliation;
- [ ] мониторинг, поддержка и окно наблюдения назначены;
- [ ] секреты и test data проверены;
- [ ] release decision зафиксирован.

## 29. Rollback Checklist

- [ ] определён измеримый trigger отката;
- [ ] зафиксирован владелец решения;
- [ ] известны обратимые и необратимые изменения;
- [ ] сохранён AS IS baseline;
- [ ] проверена резервная копия или конфигурационный экспорт;
- [ ] новые записи во время окна учтены;
- [ ] интеграции можно безопасно остановить;
- [ ] откат протестирован на стенде;
- [ ] после отката выполняются smoke и reconciliation;
- [ ] подготовлена коммуникация пользователям.

## 30. Automation Strategy

Автоматизировать следует стабильные, повторяемые и критичные проверки. Исследовательское тестирование, UAT и оценка UX остаются преимущественно ручными.

| Уровень | Кандидаты | Требование |
|---|---|---|
| Contract | REST schema/error handling | Без реальных секретов |
| Service | CRUD и transition rules | Изолированные synthetic entities |
| End-to-end | 3–5 critical journeys | Минимум UI-зависимости |
| Data | Reconciliation и formulas | Версионированные expected results |
| Security | Permission matrix | Отдельные тестовые роли |

```text
Many contract/service tests -> fewer integration tests -> few stable E2E -> manual UAT
```

Каждый automation tool имеет README, тесты, журнал изменений, dry-run для массовых действий, явные timeout/error handling и безопасную очистку по `run-id`.

## 32. Полный чек-лист QA перед сдачей проекта

### Контекст и управление

- [ ] зафиксированы Cloud/On-Premise, тариф/редакция, версия и права;
- [ ] scope, out of scope, требования и риски согласованы;
- [ ] назначены QA owner, business owner и release owner;
- [ ] критерии входа, выхода и остановки утверждены;
- [ ] изменения сопоставлены с зависимостями.

### Окружение и данные

- [ ] тестовая среда изолирована и имеет паспорт;
- [ ] конфигурационный baseline сохранён;
- [ ] используются только синтетические данные;
- [ ] внешние сервисы направлены в sandbox;
- [ ] очистка ограничена точными `run-id`;
- [ ] секреты отсутствуют в репозитории, логах и evidence.

### CRM и автоматизация

- [ ] CRUD, поля, связи, стадии и направления проверены;
- [ ] дубли и повторные обращения покрыты;
- [ ] роботы проверены при первом и повторном входе;
- [ ] все ветви БП, ожидания и ошибки покрыты;
- [ ] нет циклов, гонок и двойных side effects;
- [ ] Smart Process проверен по типу, категории и связям.

### Интеграции

- [ ] REST contract подтверждён официальным reference;
- [ ] timeout, retry, pagination и partial result проверены;
- [ ] webhook duplicate и out-of-order обработаны;
- [ ] external ID и идемпотентность проверены;
- [ ] отзыв секрета и минимальный scope протестированы;
- [ ] reconciliation и observability готовы.

### Права и безопасность

- [ ] матрица проверена целевыми ролями;
- [ ] positive и negative cases пройдены через UI и API;
- [ ] прямые ссылки, поиск, export, BI и файлы не обходят права;
- [ ] административные и временные права минимальны;
- [ ] evidence обезличены;
- [ ] security tests выполнены в согласованном scope.

### Данные, BI и миграция

- [ ] mapping и мастер-системы согласованы;
- [ ] rehearsal выполнен на тестовой выборке;
- [ ] source balance, поля, связи и суммы сверены;
- [ ] повтор миграции не создаёт дубли;
- [ ] BI formulas, grain, timezone, filters и refresh проверены;
- [ ] ограничения достоверности задокументированы.

### Производительность и надёжность

- [ ] профиль нагрузки и безопасные пределы согласованы;
- [ ] baseline и percentiles сохранены;
- [ ] очереди, ошибки и восстановление наблюдаемы;
- [ ] stop conditions соблюдены;
- [ ] Cloud/On-Premise ожидания разделены;
- [ ] recovery scenario подтверждён.

### Релиз и приёмка

- [ ] smoke, regression и UAT завершены;
- [ ] defects triaged, residual risk принят;
- [ ] backup, rollback trigger и rollback owner готовы;
- [ ] release checklist подписан;
- [ ] post-release smoke и окно наблюдения назначены;
- [ ] документация, test report и known limitations переданы.
