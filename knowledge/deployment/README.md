# Bitrix24 Deployment Engineering Knowledge Base

Инженерная база знаний для планирования, выпуска, развёртывания и контролируемого отката решений Bitrix24. Документ рассчитан на Senior Bitrix24 Solution Architect, Release Manager, DevOps Engineer и Implementation Lead.

> **Статус сведений:** факты о Bitrix24 основаны только на официальных источниках из `knowledge/SOURCES.md`. Конкретные функции, названия настроек, лимиты, способы резервирования и переноса конфигурации зависят от Cloud/On-Premise, тарифа или редакции, версии, модулей и прав. Неподтверждённая возможность помечается **«требует проверки»**.

> **Рекомендация архитектора:** deployment — управляемое изменение действующей системы, а не копирование настроек «по памяти». Для каждого выпуска обязательны AS IS, scope, зависимости, тесты, владелец решения, окно, коммуникация, контроль результата и практически выполнимый rollback.

> **Безопасность:** клиентские данные, выгрузки, резервные копии, секреты, URL действующих webhook и технические журналы с персональными данными не хранятся в Git. Примеры используют только синтетические значения.

## 1. Архитектура процесса Deployment

Deployment включает governance, подготовку, техническое изменение, проверку и передачу в сопровождение.

```text
Requirement -> Design -> Change set -> Test -> Approval -> Release window
      -> Backup/checkpoint -> Deploy -> Smoke -> Business verification
      -> Observe -> Close
                     \-> Rollback -> Verify -> Incident review
```

| Контур | Вход | Контроль | Выход |
|---|---|---|---|
| Governance | Одобренное требование | Scope, owner, risk | Release decision |
| Configuration | Реестр изменений | Peer review, dependency map | Воспроизводимый change set |
| Data | Mapping и выборка | Dry-run, reconciliation | Проверяемый результат |
| Integration | Контракты | Retry, idempotency, secrets | Стабильный обмен |
| Operations | Runbook | Window, monitoring, rollback | Передача в поддержку |

**Release gate:** нельзя начинать внедрение без готового плана отката, кроме отдельно согласованного необратимого изменения с принятым риском и альтернативным recovery plan.

## 2. Подготовка production

Production readiness подтверждается владельцами бизнеса, продукта, данных, безопасности и сопровождения.

- [ ] определены Cloud/On-Premise, доменная зона, тариф/редакция и версия;
- [ ] подтверждены администраторские и прикладные права;
- [ ] зафиксированы активные сущности, поля, стадии, роботы, БП и интеграции;
- [ ] известны критичные пользователи, часы работы и допустимый простой;
- [ ] тестовый контур или безопасная пилотная область готовы;
- [ ] production endpoints, секреты и получатели сверены без публикации значений;
- [ ] backup/checkpoint и rollback проверены;
- [ ] мониторинг и контакты эскалации доступны.

Запрещено использовать production как первый тестовый контур или выполнять массовую операцию без dry-run и тестовой выборки.

## 3. Cloud Deployment

В Cloud поставщик управляет платформой; команда проекта управляет доступными настройками, данными, автоматизациями, приложениями и REST-интеграциями в пределах тарифа и прав. Доступа к серверному PHP, БД и ядру нет.

```text
Approved configuration
   -> Portal settings / CRM / automation / supported apps / REST
   -> Pilot scope -> Verification -> Controlled rollout
```

| Зона | Допустимый подход | Ограничение |
|---|---|---|
| CRM configuration | Малые документированные изменения | Способ экспорта/импорта каждой настройки требует проверки |
| Automation | Пилотная стадия/воронка при возможности | Не включать массово без теста |
| REST/webhooks | Версионированный внешний сервис | Учитывать права, лимиты, timeout и отзыв доступа |
| Marketplace | Проверка приложения, прав и поддержки | Доступность зависит от тарифа/региона/приложения |
| Data migration | Dry-run, batch report, reconciliation | Не считать импорт rollback-механизмом |

**Рекомендация архитектора:** для работающей CRM предпочитать параллельную настройку, ограниченный пилот и поэтапное включение пользователей.

## 4. On-Premise Deployment

В On-Premise владелец дополнительно отвечает за ОС, web/PHP, БД, файловую систему, cron/агенты, очереди, резервное копирование, обновления, capacity и безопасность. Версии и поддерживаемые механизмы сверяются с [официальной документацией коробочного Bitrix24](https://dev.1c-bitrix.ru/docs/portal.php).

```text
Source/change -> Review -> Staging compatible with production
 -> Full backup + restore proof -> Maintenance window
 -> Supported deployment -> DB/module checks -> Application smoke
```

- [ ] проверена совместимость редакции, версии PHP, модулей и инфраструктуры;
- [ ] стенд сопоставим с production;
- [ ] изменения не затрагивают ядро продукта;
- [ ] резервируются согласованные БД и файлы;
- [ ] restore test подтверждён;
- [ ] cron/агенты, очереди, web и файловые права проверяются после выпуска;
- [ ] предусмотрено влияние обновлений ядра и модулей;
- [ ] инфраструктурный rollback согласован с прикладным.

Прямые изменения БД и ядра не считаются стандартной стратегией deployment и не применяются без официального поддерживаемого основания.

## 5. Предрелизная проверка

| Gate | Доказательство | Блокирующее условие |
|---|---|---|
| Scope | Change register | Неизвестные изменения |
| QA | Test report | Critical/High defect без принятия риска |
| UAT | Подпись владельца | Критический путь не принят |
| Security | Access/secrets review | Утечка или избыточный доступ |
| Data | Dry-run/reconciliation | Несбалансированная миграция |
| Operations | Runbook/monitoring | Нет владельца или rollback |
| Communication | Уведомления готовы | Пользователи не знают об остановке |

- [ ] release artifact или пошаговый change set идентифицирован;
- [ ] дата baseline и environment passport актуальны;
- [ ] known limitations перечислены;
- [ ] команды и ответственные подтвердили доступность;
- [ ] no-go criteria сформулированы до окна.

## 6. Проверка зависимостей

Изменение поля проверяется в карточках, обязательности, фильтрах, роботах, триггерах, БП, документах, REST, BI, импорте и экспорте. Изменение стадии — в автоматизациях, правах, отчётах и активных элементах.

```text
Changed item
 +- UI/cards
 +- Data/relations
 +- Automation
 +- Permissions
 +- REST/webhooks/apps
 +- BI/reports
 +- Users/support
```

| Зависимость | Вопрос | Проверка |
|---|---|---|
| Entity/field | Кто мастер и кто пишет? | Data ownership matrix |
| Stage | Какие действия запускаются? | Transition inventory |
| Role | Кто потеряет/получит доступ? | Positive/negative tests |
| Integration | Какой contract изменится? | Consumer impact |
| BI | Изменится grain/formula? | Control dataset |
| External provider | Есть ли отдельное окно? | Joint runbook |

## 7. Backup Strategy

Backup strategy задаёт scope, RPO, RTO, владельца, шифрование, срок хранения, расположение и регулярный restore test.

| Контекст | Подход | Ограничение |
|---|---|---|
| Cloud | Использовать официально доступные средства и согласованные выгрузки | Экспорт не считать полной резервной копией портала |
| On-Premise | Согласованная резервная копия БД, файлов и необходимой конфигурации | Нужны целостность и совместимость компонентов |
| Integration service | Код, конфигурация без секретов, state/checkpoint | Backup не должен раскрывать токены и ПДн |

```text
Backup -> Integrity check -> Protected storage -> Isolated restore
       -> Technical verification -> Business sample -> Evidence
```

- [ ] backup завершён до изменения;
- [ ] timestamp и scope подтверждены;
- [ ] доступ ограничен;
- [ ] restore procedure актуальна;
- [ ] последняя проверка восстановления успешна;
- [ ] новые записи после checkpoint будут обработаны.

## 8. Rollback Strategy

Rollback проектируется одновременно с change set. Он возвращает согласованное безопасное состояние, а не обязательно «полностью стирает историю».

| Изменение | Предпочтительный откат | Риск |
|---|---|---|
| Настройка | Обратный change set | Configuration drift |
| Автоматизация | Контролируемое выключение/возврат версии | Уже выполненные side effects |
| Интеграция | Предыдущая версия и остановка consumer | Накопленная очередь |
| Миграция | Точная компенсация по migration ID | Новые production-изменения |
| On-Premise | Согласованный restore/версия | Потеря данных после checkpoint |

**Правило:** массовое удаление импортированных сущностей допустимо только по точной карте идентификаторов, после согласования и проверки зависимостей; широкий фильтр запрещён.

## 9. План внедрения

План содержит последовательность, длительность, исполнителя, предусловия, ожидаемый результат, evidence, stop condition и rollback step.

```text
T-7d approve -> T-1d freeze/check -> T0 backup -> deploy batches
 -> smoke -> business check -> observe -> handover -> close
```

### Сценарий: безопасное изменение CRM

1. Зафиксировать AS IS и зависимости.
2. Настроить на тестовом контуре или пилотной воронке.
3. Выполнить regression и UAT.
4. Подготовить обратные шаги.
5. Внести одно логическое изменение.
6. Выполнить smoke и сверку данных.
7. Расширить охват только после успешного пилота.

### Сценарий: интеграционный релиз

1. Подтвердить API contract и scopes.
2. Развернуть backward-compatible consumer.
3. Проверить sandbox и synthetic event.
4. Переключить ограниченный поток.
5. Контролировать ошибки, очередь и дубли.
6. Расширить трафик или вернуть предыдущую версию.

## 10. Release Window

| Параметр | Требование |
|---|---|
| Start/end | Точные дата, время и timezone |
| Business impact | Простой, ограничение функций, затронутые группы |
| Freeze | Какие изменения запрещены |
| Staffing | Release owner, исполнители, QA, business, support |
| Checkpoints | Время go/no-go и rollback deadline |
| Communication | Каналы и шаблоны сообщений |

- [ ] окно согласовано с бизнесом и провайдерами;
- [ ] нет конфликтующего релиза;
- [ ] специалисты доступны до конца observation window;
- [ ] stop condition и крайний срок отката известны;
- [ ] смена часовых поясов исключена.

## 11. Smoke Check после внедрения

Smoke должен быть коротким и безопасным.

- [ ] целевой пользователь входит и видит разрешённую область;
- [ ] основная CRM-сущность создаётся с синтетическими данными;
- [ ] ключевой переход выполняется;
- [ ] автоматизация запускается один раз;
- [ ] критичная интеграция принимает тестовый запрос;
- [ ] запрещённое действие остаётся запрещённым;
- [ ] история и безопасные логи содержат ожидаемый след;
- [ ] мониторинг не показывает рост ошибок или очереди.

## 12. Проверка CRM

| Область | Проверка после deployment |
|---|---|
| Entities | Create/read/update и связи |
| Fields | Тип, обязательность, значения, карточка |
| Pipelines | Стадии, направления, переходы |
| Permissions | Целевая и запрещённая роль |
| Automation | Один ожидаемый side effect |
| Analytics | Даты, суммы, источник и ответственный |

Дополнительно проверяются дубли, активные сделки, экспорт и массовые действия. Удаление production-объекта для smoke не используется.

## 13. Проверка Business Processes

- [ ] способ запуска подтверждён;
- [ ] входные параметры и константы корректны;
- [ ] условия ведут в ожидаемую ветвь;
- [ ] исполнители имеют доступ;
- [ ] ожидание, срок и эскалация работают;
- [ ] ошибка видима и не оставляет ложный успех;
- [ ] повторный запуск не создаёт дубль;
- [ ] экземпляр корректно завершается.

Точный набор активностей зависит от версии, сущности и настроек портала.

## 14. Проверка Smart Processes

Проверяются тип, `entityTypeId`, категории, стадии, поля, связи, права, автоматизация и доступные операции `crm.item.*`. Контракт методов — в [официальном REST API reference](https://apidocs.bitrix24.ru/api-reference/), продуктовый контекст — в [официальной статье](https://helpdesk.bitrix24.ru/open/18913884/).

```text
Type -> Category -> Stage -> Item -> Relations
                     |        |
                  Automation  Permissions/REST
```

## 15. Проверка REST

- [ ] method и параметры подтверждены официальным reference;
- [ ] production URL и scope сверены без вывода секрета;
- [ ] timeout и обработка HTTP/API ошибок включены;
- [ ] pagination и минимальный `select` проверены;
- [ ] retry ограничен и идемпотентен;
- [ ] batch проверяет результат каждой команды;
- [ ] dry-run и batch report готовы для массовой операции;
- [ ] rollback/resume используют устойчивые ID.

## 16. Проверка Webhooks

Входящий webhook рассматривается как секретный REST endpoint; исходящий — как событие, требующее валидации и идемпотентной обработки. Детали проверяются по [официальной документации REST](https://apidocs.bitrix24.ru/).

| Контроль | Проверка |
|---|---|
| Secret | Не опубликован, доступ минимален, отзыв возможен |
| Endpoint | HTTPS, timeout и безопасный ответ |
| Delivery | Duplicate/out-of-order не создаёт дубль |
| Queue | Backlog и dead-letter наблюдаемы |
| Cutover | Старый и новый обработчики не дают двойной эффект |

Не предполагать подпись, гарантированный порядок или конкретную retry policy без официального подтверждения.

## 17. Проверка телефонии

Телефония зависит от региона, способа подключения и внешнего провайдера. Официальная отправная точка — [варианты подключения телефонии](https://helpdesk.bitrix24.ru/open/6450911/).

- [ ] входящий и исходящий тест выполняются синтетическим номером;
- [ ] caller ID нормализуется и не создаёт ложный дубль;
- [ ] очередь, рабочее время и fallback проверены;
- [ ] CRM-карточка и активность связаны корректно;
- [ ] права на звонки и записи подтверждены;
- [ ] реальный получатель не участвует без согласования;
- [ ] план возврата маршрута согласован с провайдером.

## 18. Проверка интеграций

```text
Source -> Contract -> Queue/adapter -> Bitrix24 -> Reconciliation
   ^          |             |              |
master      version      retry/DLQ       external ID
```

| Контроль | Критерий |
|---|---|
| Master system | Для каждого типа данных одна система-владелец |
| Mapping | Поля, типы, справочники и валюты версионированы |
| Identity | External ID и правила дублей устойчивы |
| Reliability | Timeout, retry, idempotency, replay |
| Observability | Correlation ID без ПДн, metrics, alerts |
| Recovery | Reconciliation и controlled replay |

## 19. Проверка BI

Доступность BI Конструктора и datasets зависит от тарифа и конфигурации. Использовать [официальную документацию по наборам данных](https://helpdesk.bitrix24.ru/open/24355590/).

- [ ] dataset, grain, dimensions и measures подтверждены;
- [ ] timezone, валюта и округление согласованы;
- [ ] row count и контрольная выборка сверены;
- [ ] фильтры, права и обезличивание не изменились;
- [ ] refresh и поздние изменения учитываются;
- [ ] dashboard сопоставлен с мастер-источником;
- [ ] расхождения документированы до закрытия релиза.

## 20. Feature Flags

Универсальный штатный механизм feature flags для всех компонентов Bitrix24 в используемых источниках не подтверждён. Применимость каждого механизма **требует проверки**.

| Механизм управления включением | Когда допустим | Ограничение |
|---|---|---|
| Пилотная воронка/стадия | Изоляция нового процесса | Не всегда применимо к общей сущности |
| Ограниченная роль/группа | Постепенный доступ | Не подменять безопасность |
| Настройка внешнего сервиса | Версионированная интеграция | Flag хранится вне Bitrix24 |
| Параллельный endpoint | Интеграционный cutover | Нужна защита от двойной обработки |

Flag имеет owner, default, аудит, срок удаления, fail-safe состояние и тест обоих значений.

## 21. Управление конфигурацией

Configuration register фиксирует объект, текущее и целевое состояние, зависимости, автора, проверяющего, дату, environment и rollback.

| Объект | Минимальная запись |
|---|---|
| Поле | Entity, code, type, required stage, usage |
| Стадия | Pipeline, semantic meaning, automation, permissions |
| Робот/БП | Trigger, condition, action, actor, retry, error |
| Webhook/app | Owner, scope, purpose, revoke; без секрета |
| BI | Dataset, formula, grain, refresh, owner |

Не предполагать универсальный полный export/import конфигурации. Воспроизводимость обеспечивается доступными официальными средствами плюс точный change register.

## 22. Версионирование изменений

```text
Change ID -> Design version -> Test evidence -> Release version
          -> Deployment record -> Current configuration baseline
```

Каждый релиз имеет уникальный ID, дату, scope, совместимость, миграционные шаги, rollback, changelog и ссылки на evidence. Семантическое версионирование можно применять к собственному коду и контрактам; оно не объявляется версией портала Bitrix24.

## 23. Управление рисками

| Риск | Вероятность | Влияние | Мера | Trigger |
|---|---|---|---|---|
| Потеря данных | Оценить | Critical | Backup, dry-run, IDs | Reconciliation mismatch |
| Раскрытие данных | Оценить | Critical | Least privilege, tests | Unauthorized access |
| Дубли | Оценить | High | Idempotency | Duplicate rate |
| Остановка процесса | Оценить | High | Pilot, rollback | Critical journey fails |
| BI mismatch | Оценить | Medium/High | Control totals | Threshold exceeded |
| Provider failure | Оценить | High | Joint fallback | Error/backlog threshold |

Риск имеет владельца, остаточный уровень и формальное принятие; цвет без критериев не является управлением риском.

## 24. План коммуникации

| Аудитория | До | Во время | После |
|---|---|---|---|
| Пользователи | Время, влияние, инструкция | Статус при отклонении | Результат и ограничения |
| Руководители | Риск и решение go/no-go | Эскалация | KPI и residual risk |
| Support | Runbook и known issues | Incident intake | Handover |
| Providers | Joint window | Shared bridge | Reconciliation |

- [ ] назначен единый release channel;
- [ ] статусы имеют согласованную периодичность;
- [ ] сообщения не содержат секретов и ПДн;
- [ ] шаблоны success, delay, rollback и incident готовы;
- [ ] решение go/no-go сообщает только уполномоченный владелец.

## 25. Документирование внедрения

Deployment record включает:

- release ID и цель;
- фактические start/end и исполнителей;
- выполненные шаги и отклонения;
- идентификатор backup без пути/секрета;
- результаты smoke, business check и reconciliation;
- дефекты, ограничения и принятые риски;
- решение success/rollback;
- фактический rollback, если был;
- задачи поддержки и срок наблюдения.

Конфиденциальные журналы и клиентские доказательства остаются в разрешённой локальной или корпоративной системе, а не в Git.

## 26. Контроль успешности

```text
Technical health + Business journey + Data integrity + User impact
                 -> Success criteria -> Observation window -> Closure
```

| Измерение | Пример критерия |
|---|---|
| Technical | Нет новых critical ошибок, backlog стабилен |
| Functional | Critical journeys пройдены |
| Data | Reconciliation в согласованном допуске |
| Security | Negative permission checks пройдены |
| Business | Владелец подтвердил результат |
| Operations | Support принял документацию |

Отсутствие жалоб не доказывает успешность. Критерии и observation window задаются до релиза.

## 28. Полный чек-лист внедрения

### Governance

- [ ] release ID, цель, scope и out of scope утверждены;
- [ ] release owner, technical owner, QA и business owner назначены;
- [ ] Cloud/On-Premise, тариф/редакция и версия зафиксированы;
- [ ] risks, assumptions, constraints и no-go criteria согласованы;
- [ ] approvals и change ticket доступны.

### Configuration and dependencies

- [ ] AS IS и целевой baseline сохранены;
- [ ] поля, стадии, права, роботы, БП и BI инвентаризированы;
- [ ] REST, webhooks, apps и внешние providers включены в карту;
- [ ] consumer impact и backward compatibility проверены;
- [ ] change set прошёл peer review;
- [ ] существующие пользовательские изменения сохранены.

### Testing and acceptance

- [ ] smoke, functional и targeted regression пройдены;
- [ ] negative permissions и security checks выполнены;
- [ ] migration rehearsal и reconciliation успешны;
- [ ] performance profile проверен безопасно;
- [ ] UAT подписан;
- [ ] known defects и limitations приняты владельцем.

### Backup and rollback

- [ ] backup/checkpoint соответствует scope;
- [ ] integrity и restore test подтверждены;
- [ ] RPO/RTO согласованы;
- [ ] rollback steps, trigger, owner и deadline готовы;
- [ ] side effects и новые записи учтены;
- [ ] rollback smoke и reconciliation определены.

### Release window

- [ ] start/end, timezone, freeze и impact опубликованы;
- [ ] исполнители и escalation contacts доступны;
- [ ] provider windows синхронизированы;
- [ ] communication templates готовы;
- [ ] checkpoints и go/no-go meetings назначены;
- [ ] параллельные изменения исключены.

### Execution

- [ ] backup завершён до первого изменения;
- [ ] каждый шаг имеет фактический статус и evidence;
- [ ] изменения выполняются малыми batches;
- [ ] stop conditions контролируются;
- [ ] секреты и ПДн не выводятся;
- [ ] отклонения немедленно оцениваются.

### Verification

- [ ] post-deployment smoke пройден целевыми ролями;
- [ ] CRM, БП, Smart Processes и права проверены;
- [ ] REST, webhooks, телефония и интеграции проверены;
- [ ] BI и data reconciliation выполнены;
- [ ] monitoring, error rate и backlog стабильны;
- [ ] business owner подтвердил critical journey.

### Closure and handover

- [ ] success criteria выполнены в observation window;
- [ ] deployment record и changelog завершены;
- [ ] support получил runbook, contacts и known issues;
- [ ] временные права и секреты отозваны/ротированы по плану;
- [ ] test data удалены точечно;
- [ ] follow-up actions имеют владельцев и сроки;
- [ ] release формально закрыт.

## 29. План отката

План заполняется до релиза для конкретного change set.

| Поле | Требуемое содержание |
|---|---|
| Trigger | Измеримое условие: critical journey, data mismatch, error/backlog |
| Authority | Кто принимает решение |
| Deadline | Последняя безопасная точка |
| Scope | Что возвращается и что сохраняется |
| Steps | Нумерованные обратные действия |
| Data | Новые записи, compensation, reconciliation |
| Verification | Infrastructure/app smoke и business sample |
| Communication | Кто и когда уведомляется |

```text
Trigger met -> Freeze writes/change -> Declare rollback
 -> Preserve diagnostics -> Execute reverse steps/restore
 -> Reconcile data -> Smoke -> Business confirmation
 -> Communicate -> Incident review
```

- [ ] остановить дальнейший rollout и автоматические writers;
- [ ] сохранить безопасные диагностические данные;
- [ ] зафиксировать checkpoint и затронутые ID;
- [ ] выполнить заранее проверенные обратные шаги;
- [ ] обработать очередь и новые записи по формальному правилу;
- [ ] выполнить smoke, permission test и reconciliation;
- [ ] сообщить результат и ограничения;
- [ ] открыть root-cause review до повторного deployment.
