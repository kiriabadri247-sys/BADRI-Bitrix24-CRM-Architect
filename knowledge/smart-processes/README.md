# Bitrix24 Smart Processes Engineering Knowledge Base

Инженерная база знаний для проектирования, внедрения и аудита смарт-процессов Bitrix24. Документ задаёт архитектурные правила, но не заменяет проверку конкретного портала: доступность опций, автоматизации, прав, связей и REST зависит от Cloud/On-Premise, тарифа или редакции, версии модулей и включённой конфигурации.

> **Статус сведений:** подтверждённые возможности обобщены по официальным источникам из `knowledge/SOURCES.md`. «Рекомендация архитектора» — собственное инженерное решение. Функция, не подтверждённая для целевого портала, помечается как **требующая проверки**.

> **Безопасность:** использовать только обезличенные или синтетические примеры. Пароли, токены, webhook URL, персональные данные, реальные документы и клиентские выгрузки хранить в Git запрещено.

## 1. Что такое Smart Processes

Смарт-процесс — настраиваемый тип CRM-сущности со своей карточкой, набором полей, стадиями, правами, связями и доступной автоматизацией. Он применяется, когда предметная область имеет самостоятельный жизненный цикл, но стандартные лид, сделка, контакт и компания семантически не подходят.

Официальная пользовательская отправная точка: [Как создать смарт-процесс в CRM](https://helpdesk.bitrix24.ru/open/18913884/).

### 1.1. Назначение и история

Назначение Smart Processes — моделировать корпоративные сущности без подмены стандартных CRM-объектов: договор, объект оборудования, заявка, лицензия, закупка или сервисное обращение.

Точная хронология появления и изменения функциональности не зафиксирована используемым реестром источников. Для проектного решения дата появления не используется; актуальность проверяется по текущей официальной документации и фактическому порталу. Исторические утверждения без отдельного официального источника считаются **требующими проверки**.

### 1.2. Сравнение с другими механизмами

| Механизм | Основное назначение | Когда Smart Process предпочтительнее | Когда не заменяет механизм |
|---|---|---|---|
| Стандартная CRM | Продажи и клиентские отношения через лиды, сделки, контакты и компании | Нужна отдельная предметная сущность со своим циклом | Не создавать Smart Process вместо сделки, контакта или компании без семантической причины |
| Lists | Универсальные структурированные реестры и внутренние данные в поддерживаемом контексте | Нужны CRM-связи, стадии, канбан, права и CRM-автоматизация | Простой справочник без жизненного цикла может остаться списком |
| Highload-блоки | Коробочный механизм высокопроизводительного хранения структурированных данных | Нужен пользовательский CRM-интерфейс и управляемый жизненный цикл | Highload-блоки относятся к On-Premise-разработке; точная применимость и API требуют проверки версии |
| Универсальные сущности | Термин может означать универсальную CRM-модель и методы | Smart Process является пользовательским типом в универсальной модели CRM | Не считать «универсальную сущность» отдельным подтверждённым продуктом без определения термина |
| Задачи | Исполнимая работа с ответственным, сроком и результатом | Нужен объект, который проходит собственные стадии и порождает задачи | Smart Process не заменяет человеческую работу внутри задачи |
| Внешняя система | Специализированная учётная, производственная или сервисная платформа | Bitrix24 должен быть операционным интерфейсом и хранить согласованный поднабор данных | Не переносить в CRM сложное ядро внешней системы без обоснования |

**Рекомендация архитектора:** сначала проверить стандартные CRM-сущности, поля, карточки, роботов, БП, списки и задачи. Smart Process создаётся только при наличии самостоятельного объекта и жизненного цикла.

## 2. Архитектура Smart Processes

### 2.1. Основные понятия

| Понятие | Инженерное определение | Контроль |
|---|---|---|
| Entity Type | Тип CRM-сущности, определяющий модель Smart Process | Уникальный системный идентификатор и настройки типа не угадывать |
| Factory | Слой универсальной CRM-модели, предоставляющий метаданные и работу с типом | REST-доступность и контракт проверять по официальному API |
| Item | Конкретный элемент Smart Process | Базовые свойства: ID и схема доступных полей; фактический набор определяется метаданными типа |
| Conditional capabilities | Стадии, воронки, клиентские связи, товары, источники, ответственный, автоматизация и другие подключаемые возможности | Могут быть отключены настройками типа; наличие и REST-контракт не предполагать |
| Stages | Условно доступные состояния жизненного цикла элемента | Если стадии включены, для каждой определить вход, выход, SLA и бизнес-смысл |
| Categories | Категории/направления, если включены и поддерживаются типом | Не предполагать наличие нескольких категорий без проверки настройки |
| Pipelines | Бизнес-представление отдельных жизненных циклов через категории и стадии | Термин использовать как архитектурное понятие; точное UI-название проверять |
| Relations | Связи с CRM-элементами и другими поддерживаемыми объектами | Фиксировать направление, множественность, права и удаление |

### 2.2. Взаимосвязи

```text
Entity Type
├── configuration and capabilities
├── fields
├── permissions
└── categories / pipelines (if enabled)
    └── stages
        └── items
            ├── field values
            ├── responsible user
            ├── automation
            └── relations to CRM and other supported entities
```

```text
Factory metadata → entityTypeId → crm.item operations → Item
                                            ├── Category
                                            ├── Stage
                                            ├── User fields
                                            └── Relations
```

Конфигурация типа является контрактом. Перед проектированием интеграции обязательны metadata discovery и capability inventory целевого типа: поля, стадии, воронки, клиентские связи, товары, источники, права и автоматизация. Возможность включения отдельных функций подтверждается по [официальной настройке Smart Process](https://helpdesk.bitrix24.ru/open/18913884/) и контракту [`crm.item.add`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html) (проверено 2026-08-10). Изменение включённых возможностей после запуска требует анализа действующих элементов, прав, REST, роботов, БП, документов и аналитики.

## 3. Где использовать Smart Processes

| Сценарий | Преимущества | Ограничения | Когда не использовать |
|---|---|---|---|
| Договоры | Отдельная карточка, стадии подготовки/согласования/подписания, связи с клиентом и сделкой | Версии файлов, юридическая значимость и подписание требуют отдельной архитектуры | Если договор полностью управляется ECM/1С и CRM нужна только ссылка |
| Оборудование | Реестр объектов, ответственный, статус, связь с клиентом/сервисом | Большие телеметрические данные и складской учёт не предназначены для карточки CRM | Для IoT, серийного учёта и высокочастотных событий лучше профильная система |
| Проекты | Жизненный цикл инициативы и связь с продажей | Smart Process не заменяет задачи, загрузку ресурсов и полноценное управление проектом | Если достаточно штатных проектов и задач |
| Заявки | Единая карточка обращения, маршрутизация, SLA и исполнители | Большой контакт-центр может требовать специализированный сервис-деск | Для простой одношаговой просьбы достаточно задачи/формы |
| Сервис | Обращение, диагностика, решение, подтверждение клиента | Нужны SLA, очередь, приоритет и защита персональных данных | При требованиях ITSM, CMDB и сложных SLA — специализированная система |
| HR | Заявки, адаптация, кадровые маршруты | Особые категории персональных данных и права | Не хранить кадровое досье без правового и технического обоснования |
| Закупки | Инициатива, согласование, поставщик, бюджет, статус | Финансовые обязательства и заказы могут быть мастер-данными ERP | Если процесс полностью ведётся в 1С/ERP |
| Объекты | Объект недвижимости, площадка или иной предметный объект | Геоданные, иерархия и версии могут потребовать внешнюю систему | Для простого справочника без стадий — Lists/справочник |
| Лицензии | Срок, владелец, продукт, продление и связь с клиентом | Секретные ключи лицензий нельзя хранить без отдельной защиты | Не хранить пароли и ключи как обычные поля CRM |
| Документы | Реестр и маршрут подготовки/согласования | Smart Process не является полноценным защищённым архивом | Если нужны ECM, юридически значимое хранение и строгая версионность |

Перед выбором проверить объём, частоту изменений, роли, поиск, аналитику, интеграции, срок хранения и мастер-систему.

## 4. Поля

### 4.1. Классификация

| Вид поля | Назначение | Ограничения и рекомендации |
|---|---|---|
| Стандартное | Системные свойства элемента: ID, название, стадия, ответственный и другие включённые возможности | Не дублировать пользовательским полем; точный состав зависит от типа |
| Пользовательское | Предметный атрибут конкретной модели | Фиксировать внутренний код, тип, владельца, обязательность и зависимости |
| Обязательное | Данные, без которых нельзя выполнить контрольную точку | Делать обязательным на нужной стадии, если поддерживается; не блокировать раннюю регистрацию |
| Вычисляемое | Значение, полученное из других данных | Наличие штатного вычисляемого типа/механизма **требует проверки**; часто расчёт выполняет автоматизация или BI |
| Множественное | Несколько значений одного типа | Усложняет фильтрацию, документы, REST и аналитику; использовать только при реальной множественности |
| Файловое | Связанный файл или документ | Права, размер, версии, персональные данные и срок хранения проверять отдельно |
| Привязка | Связь с CRM или поддерживаемым объектом | Хранить системную связь, а не отображаемое название или текстовый ID |

### 4.2. Паспорт пользовательского поля

Для каждого поля документируются:

- отображаемое название и стабильный внутренний код;
- Entity Type и назначение;
- тип, множественность, формат, диапазон и точность;
- допустимые значения и правила изменения справочника;
- обязательность и стадия контроля;
- мастер-система и ответственный за заполнение;
- права чтения и изменения;
- использование в карточке, фильтрах, роботах, БП, REST, документах, BI, импорте и экспорте;
- миграция, архивирование и тест.

### 4.3. Рекомендации архитектора

- использовать поле только при наличии бизнес-потребителя;
- выбирать структурированный тип вместо свободного текста для аналитики;
- не хранить секреты, большие JSON payload и журналы интеграции;
- внешний ID создавать для идемпотентной интеграции;
- не кодировать состояние набором булевых полей вместо стадий;
- перед изменением поля проверить все зависимости;
- удаление поля выполнять только после выгрузки, анализа и согласованной миграции.

## 5. Стадии

Стадия описывает бизнес-состояние элемента, а не действие сотрудника. Жизненный цикл должен иметь начало, рабочие состояния, успешные/неуспешные исходы и правила возврата.

| Аспект | Архитектурное правило |
|---|---|
| Жизненный цикл | Для каждой стадии определить вход, выход, владельца, SLA и обязательные данные |
| Categories | Отдельная категория нужна для самостоятельного жизненного цикла, а не только другого продукта |
| Несколько воронок | Допустимы при разных ролях, стадиях, правах, автоматизации или аналитике; наличие опции проверяется |
| Права | Проверять чтение, изменение, переход, удаление и экспорт по ролям |
| Автоматизация | Роботы/триггеры/БП не должны циклически возвращать элемент |
| Переходы | Запрещать или контролировать логически невозможные переходы; фактический механизм ограничения требует проверки |

Пример универсального цикла:

```text
New → Validation → In progress → Approval → Completed
                    └────────────→ Rejected / Cancelled
```

Перед изменением стадии проверить роботов, триггеры, БП, связи, отчёты, активные элементы, документы и внешние интеграции.

## 6. Автоматизация

Официальный контекст: [Роботы и триггеры в Bitrix24](https://helpdesk.bitrix24.ru/open/24633726/) и [Как выбрать тип бизнес-процесса](https://helpdesk.bitrix24.ru/open/23951294/).

| Механизм | Когда использовать | Ограничения |
|---|---|---|
| Робот | Короткое действие при стадии/условии: задача, уведомление, изменение поля в доступном наборе | Точный состав действий зависит от портала; длинные цепочки становятся непрозрачными |
| Триггер | Реакция на поддерживаемое событие и возможный переход | Повторы и обратные переходы требуют защиты; список событий проверяется |
| Бизнес-процесс | Многошаговый маршрут, согласование, ветвление, ожидание и роли | Нужны версия, SLA, обработка ошибок и контроль активных экземпляров |
| Событие/REST | Связь с внешней системой через опубликованный контракт | Не предполагать наличие конкретного события; timeout, retry и идемпотентность обязательны |

### 6.1. Правила

- один механизм имеет одного владельца результата;
- карта автоматизаций показывает, кто меняет каждое поле и стадию;
- повторный запуск не создаёт дубли задач, элементов и документов;
- внешняя операция получает operation ID и журнал результата;
- массовая автоматизация сначала проверяется на одном синтетическом элементе;
- ошибка видима, классифицирована и имеет эскалацию;
- Cloud ограничен штатными возможностями тарифа;
- On-Premise-расширение не изменяет ядро и проходит тест обновления.

## 7. REST API

Официальный контракт проверяется в [Bitrix24 REST API](https://apidocs.bitrix24.ru/) и [справочнике API](https://apidocs.bitrix24.ru/api-reference/).

### 7.1. Универсальная модель

| Компонент | Использование |
|---|---|
| `crm.item.*` | Универсальные операции над поддерживаемыми CRM-элементами, включая Smart Processes |
| `entityTypeId` | Обязательный контекст типа; получать/хранить в конфигурации tenant, не угадывать |
| Factory/type metadata | Определение типа, полей и доступных возможностей по опубликованному контракту |
| Item ID | Идентификатор конкретного элемента внутри типа |
| Fields | Системные и пользовательские значения; schema discovery выполняется до mapping |
| Category/stage | Контекст жизненного цикла; значения не переносить между порталами без mapping |

### 7.2. Операции

Не перечисляя неподтверждённые имена, интеграция проектирует документированные операции создания, чтения одного элемента, списка, обновления, удаления и получения метаданных. Для каждой операции проверяются точное имя метода, обязательные параметры, права, формат ответа и ошибки.

Удаление по умолчанию не автоматизируется. Нужны согласование, dry-run, проверка связей, отчёт и план восстановления.

### 7.3. Пользовательские поля и массовые операции

- mapping строится по внутренним кодам, не по отображаемым названиям;
- тип и множественность валидируются по metadata;
- enum-значения нельзя переносить по подписи без mapping;
- массовая операция поддерживает dry-run, малую выборку, очередь, ограниченный batch, checkpoint и reconciliation;
- внешний ID и operation ID защищают от дублей;
- точные batch-лимиты не фиксируются без подтверждённого источника.

Подробные общие правила REST находятся в `knowledge/rest-api/README.md`.

## 8. Связи

### 8.1. Матрица связей

| Связанный объект | Типовой смысл | Архитектурный контроль |
|---|---|---|
| Сделка | Источник договора, проекта, сервиса или исполнения | Одна связь не должна скрывать несколько независимых возможностей |
| Лид | Исходное неквалифицированное обращение | После квалификации определить актуальную связь с клиентом и сделкой |
| Компания | Юридическое лицо, владелец или заказчик | Название не является уникальным ключом |
| Контакт | Представитель или физическое лицо | Персональные данные и множественные роли |
| Другой Smart Process | Иерархия или предметная связь | Направление, множественность, каскадные последствия и права |

### 8.2. Схемы

```text
Company ── Contacts
   │
   └── Deal ── Contract (Smart Process)
                 ├── Documents
                 └── Service Request (Smart Process)
```

```text
Deal ── Project (Smart Process)
          ├── Equipment Items (Smart Process)
          ├── Tasks
          └── Purchase Request (Smart Process)
```

Связь проектируется как отдельный контракт: источник, назначение, обязательность, множественность, доступ, создание, изменение, удаление и REST mapping. Нельзя дублировать связь текстовым полем «ID сделки» без обоснования.

## 9. Проектирование

### 9.1. Методика архитектора

До создания определить:

| Область | Вопрос |
|---|---|
| Цель | Какую проблему решает сущность и что считается результатом |
| Владелец | Кто отвечает за процесс, данные, права и сопровождение |
| Жизненный цикл | Какие состояния, переходы, SLA и исходы существуют |
| Роли | Кто создаёт, читает, изменяет, переводит, экспортирует и удаляет |
| Права | Свои/отдел/все и специальные ограничения в доступной модели |
| Автоматизация | Робот, триггер, БП, задача или внешний сервис для каждого действия |
| Интеграции | Мастер-система, внешний ID, mapping, направление, retry и мониторинг |
| Отчёты | Какие показатели нужны и из каких качественных данных они рассчитываются |

### 9.2. Чек-лист проектирования

- [ ] Подтверждены Cloud/On-Premise, тариф/редакция, версия и права администратора.
- [ ] Стандартные CRM-сущности, Lists, задачи и внешняя система рассмотрены как альтернативы.
- [ ] Есть самостоятельная сущность и измеримый жизненный цикл.
- [ ] Назначены владелец процесса и владелец данных.
- [ ] Определены источник создания и правила архивирования/удаления.
- [ ] Стадии имеют вход, выход, SLA и ответственного.
- [ ] Категории создаются только для разных жизненных циклов.
- [ ] Поля имеют паспорт, владельца и потребителя.
- [ ] Связи имеют направление и множественность.
- [ ] Роли и права протестированы неадминистративными пользователями.
- [ ] Карта автоматизаций исключает циклы и дубли.
- [ ] Интеграции имеют внешний ID, timeout, retry и reconciliation.
- [ ] Аналитика проектируется до запуска.
- [ ] Подготовлены синтетические тестовые данные, пилот и откат.
- [ ] Обновлены реестры полей, стадий, автоматизаций, интеграций и тестов.

## 10. Права доступа

Точная модель прав Smart Process и её интерфейс зависят от портала и включённых возможностей. Наследование от CRM, организационной структуры или связанного объекта нельзя предполагать без проверки.

### 10.1. Типовая ролевая матрица

| Роль | Создание | Чтение | Изменение | Смена стадии | Экспорт | Удаление |
|---|---|---|---|---|---|---|
| Исполнитель | По процессу | Свои/назначенные | Рабочие поля | Разрешённые переходы | Нет | Нет |
| Руководитель | В пределах функции | Отдел/направление | Контрольные поля | Управленческие переходы | По регламенту | Ограничено |
| Согласующий | Нет или по процессу | Назначенные элементы | Только решение/комментарий | Только согласование | Нет | Нет |
| Контролёр/аудитор | Нет | Чтение согласованного объёма | Нет | Нет | Ограничено | Нет |
| Интеграция | Только по контракту | Только по контракту | Только мастер-поля | Только если владеет статусом | API по контракту | Запрещено по умолчанию |
| Администратор | Для настройки и поддержки | По регламенту | По регламенту | Для диагностики | Только с основанием | Только с согласованием |

### 10.2. Безопасность

- роли задаются по функциям, не по фамилиям;
- группы и отделы используются только после проверки фактической модели доступа;
- связанные элементы не должны раскрывать данные пользователю без права на исходную сущность;
- отдельно тестируются прямой URL, поиск, фильтры, мобильный интерфейс, экспорт и REST;
- удаление, массовое изменение и финансовые поля получают усиленный контроль;
- персональные данные минимизируются;
- изменения прав журналируются и периодически пересматриваются.

## 11. Производительность

### 11.1. Большие объёмы

Smart Process — операционная CRM-сущность, а не безусловная замена хранилищу больших данных. До загрузки оценить количество элементов, полей, связей, файлов, ежедневных изменений, фильтров, роботов, активных БП и REST-вызовов.

| Область | Рекомендация |
|---|---|
| Индексация | В Cloud пользователь не управляет индексами БД. В On-Premise прямое изменение индексов без официального обоснования и анализа обновлений не допускается; применимость **требует проверки** |
| Массовые операции | Внешний инструмент с dry-run, очередью, checkpoint, ограниченным batch и отчётом |
| Фильтрация | Документированные поля и операторы, минимальный `select`, стабильная сортировка |
| Поиск | Не использовать свободный поиск как уникальную идентификацию; внешний ID и точные фильтры |
| Автоматизация | Массовый импорт не должен неконтролируемо запускать роботов и БП |
| Файлы | Не загружать большие объёмы без оценки хранения, прав и времени |
| Аналитика | Тяжёлые отчёты выносить в подходящий BI-контур после проверки доступных наборов |

### 11.2. Оптимизация

- архивировать по согласованному правилу, а не удалять историю;
- уменьшать число редко используемых полей и связей;
- не запрашивать все поля через REST;
- применять инкрементальную синхронизацию;
- контролировать backlog автоматизаций;
- тестировать объём на отдельном портале/воронке;
- измерять latency списка, карточки, REST, роботов и отчётов;
- для On-Premise дополнительно анализировать PHP, БД, агенты, cron, очереди и инфраструктуру.

Точные лимиты и рекомендации производительности подтверждаются официальными источниками и фактическим нагрузочным тестом; числа не придумываются.

## 12. Cloud vs On-Premise

| Возможность | Облако | Коробка | Комментарий архитектора |
|---|---|---|---|
| Smart Processes | В пределах тарифа и доступных опций | В пределах редакции и версии модулей | Проверить целевой портал до проектирования |
| Поля и карточки | Штатная конфигурация | Штатная конфигурация версии | Состав системных опций может различаться |
| Категории/воронки | При наличии опции | При наличии в версии | Не создавать без отдельного цикла |
| Роботы/триггеры | В пределах тарифа | В пределах редакции/модулей | Набор действий проверять |
| Бизнес-процессы | При наличии функции | При наличии модуля/редакции | Версионировать и тестировать |
| REST `crm.item.*` | По официальному Cloud-контракту | Зависит от версии REST-модулей | Metadata и методы проверять на портале |
| Серверный код | Недоступен | Возможны поддерживаемые модули | Ядро не изменять |
| Доступ к БД | Нет | Контролируется владельцем | Прямая запись не является безопасным API |
| Индексы БД | Не управляются клиентом | Технически управляются владельцем | Изменение только после официального анализа и теста обновлений |
| Cron/агенты | Не управляются клиентом | Управляются владельцем | Нужен мониторинг |
| Логи платформы | Ограничены интерфейсами и интеграциями | Дополнительно серверные журналы | Маскировать персональные данные и секреты |
| Обновления | Управляет поставщик | Планирует владелец | Стенд, backup и regression tests обязательны |
| Масштабирование | В рамках сервиса | Ответственность владельца | Нагрузочная модель до массового запуска |

Официальная точка входа On-Premise: [документация коробочного Bitrix24](https://dev.1c-bitrix.ru/docs/portal.php).

## 14. Практический чек-лист архитектора

### 14.1. Контекст

- [ ] Определены Cloud/On-Premise, зона, тариф/редакция и версия.
- [ ] Подтверждены права администратора и будущих ролей.
- [ ] Есть тестовый портал или тестовая воронка.
- [ ] Зафиксирован AS IS и недопустимые изменения.
- [ ] Определены владельцы процесса, данных и сопровождения.

### 14.2. Выбор сущности

- [ ] Проверены стандартные CRM-сущности, Lists, задачи и внешние системы.
- [ ] Smart Process имеет самостоятельный предмет и цикл.
- [ ] Определены источник создания и правило уникальности.
- [ ] Назначена мастер-система.
- [ ] Определены архивирование, срок хранения и удаление.

### 14.3. Тип, поля и стадии

- [ ] Зафиксированы Entity Type и `entityTypeId` для каждого tenant.
- [ ] Включены только необходимые системные возможности.
- [ ] Составлен реестр полей с внутренними кодами.
- [ ] Типы, множественность и enum mapping протестированы.
- [ ] Стадии имеют вход, выход, SLA и исход.
- [ ] Категории обоснованы разными жизненными циклами.
- [ ] Изменение схемы имеет миграцию и откат.

### 14.4. Связи и права

- [ ] Для каждой связи определены направление и множественность.
- [ ] Нет текстовых дублей системных relations.
- [ ] Составлена матрица ролей и операций.
- [ ] Проверены прямые ссылки, поиск, экспорт, мобильный UI и REST.
- [ ] Связанные закрытые объекты не раскрываются.
- [ ] Интеграционный пользователь имеет минимальные права.

### 14.5. Автоматизация и интеграции

- [ ] Составлена карта роботов, триггеров, БП и событий.
- [ ] Нет циклов и конкурирующей записи одного поля.
- [ ] Повторный запуск не создаёт дубль.
- [ ] Внешние операции имеют timeout, retry, idempotency и monitoring.
- [ ] Mapping и внешний ID задокументированы.
- [ ] Массовые операции поддерживают dry-run, checkpoint и отчёт.
- [ ] Побочные действия импорта проверены.

### 14.6. Аналитика, тестирование и запуск

- [ ] Определены KPI, источники данных и ограничения достоверности.
- [ ] Подготовлены позитивный, негативный, повторный и recovery-сценарии.
- [ ] Выполнена малая синтетическая выборка.
- [ ] Проверены права каждой роли.
- [ ] Проверены объём, фильтрация, поиск и REST pagination.
- [ ] Подготовлены backup/выгрузка и план отката.
- [ ] Пилот согласован с ограниченной группой пользователей.
- [ ] Обновлены README, реестры, диаграммы, тесты и changelog.
