# Bitrix24 Telephony Engineering Knowledge Base

Инженерная база знаний для проектирования, внедрения, диагностики и сопровождения телефонии Bitrix24. Конкретные функции зависят от региона, тарифа/редакции, версии продукта, способа подключения и внешнего провайдера.

> **Статус:** факты обобщены только по официальным источникам из `knowledge/SOURCES.md`. «Рекомендация архитектора» — проектное решение. Неподтверждённая опция, REST-метод или SIP-возможность помечается как **требующая проверки**.

> **Безопасность:** примеры синтетические. Реальные номера, SIP-логины и пароли, домены АТС, записи разговоров, webhook URL и клиентские данные в Git запрещены.

## 1. Архитектура телефонии Bitrix24

Телефония связывает оператора/провайдера, маршрутизацию звонка, пользователя Bitrix24 и CRM-контекст. Официально описаны варианты: аренда номера, подключение АТС через SIP-коннектор и подключение через REST-приложение; доступность зависит от региона и тарифа. Источник: [Как начать звонить из Bitrix24](https://helpdesk.bitrix24.ru/open/6450911/).

| Слой | Ответственность |
|---|---|
| Оператор/АТС | Номер, голосовой маршрут и телеком-услуга по выбранной модели |
| Коннектор | Поддерживаемая связь АТС с Bitrix24 |
| Bitrix24 | Пользовательский интерфейс, маршрутизация в доступном сценарии, CRM-контекст |
| CRM | Клиент, лид/сделка, активность, ответственный |
| Интеграционный слой | REST-события, mapping, очередь, мониторинг при применимости |

```text
PSTN/Provider ↔ PBX/connector ↔ Bitrix24 Telephony ↔ Employee
                                      └───────────↔ CRM
```

## 2. Облачная телефония и SIP

| Модель | Подтверждённый контекст | Архитектурный контроль |
|---|---|---|
| Аренда номера | Номер предоставляется в доступной Bitrix24-схеме | Регион, документы, тариф, владельцы и continuity |
| Облачная SIP АТС | Внешний номер подключается через SIP-коннектор при совместимости АТС | SIP-параметры, маршрутизация, оплата, тест входящих/исходящих |
| Офисная SIP АТС | Подключение собственной инфраструктуры при поддерживаемой конфигурации | NAT/firewall, доступность, failover, голосовое качество |
| REST-приложение | Подключение через официально поддерживаемое приложение провайдера | Функции зависят от приложения; не считать эквивалентом SIP |

```text
Cloud PBX ─SIP connector─> Bitrix24
Provider app ─REST app contract─> Bitrix24
```

Не подключать один номер одновременно разными способами без официального подтверждения совместимости.

## 3. Подключение внешней АТС

| Этап | Результат |
|---|---|
| Discovery | Тип АТС, номера, регион, операторы, codecs/network — при необходимости и подтверждении провайдера |
| Contract | Кто отвечает за voice, signaling, connector и CRM-события |
| Security | SIP credentials вне Git, минимальный доступ, смена пароля |
| Pilot | Один синтетический номер/группа и тестовые пользователи |
| Acceptance | Матрица входящих, исходящих, transfer, missed и fallback |
| Operations | SLA, контакты сторон, monitoring и incident routing |

```text
External PBX → supported SIP/REST connector → Bitrix24 → CRM
             ↘ provider diagnostics        ↘ CRM diagnostics
```

Конкретные SIP-параметры, codecs, порты и сетевые требования берутся у официального провайдера/документации и здесь не фиксируются.

## 4. Входящие звонки

| Шаг | Контроль |
|---|---|
| Определение номера | Какая линия/номер принял звонок |
| Поиск клиента | Нормализованный номер, права, правила дублей |
| Маршрутизация | Рабочее время, очередь, ответственные, fallback |
| CRM-контекст | Открыть корректную карточку или применить правило нового обращения |
| Результат | Ответ, пропущен, перевод, завершение и доступная фиксация |

```text
Incoming call → Number rule → Schedule → Queue → Employee
                     └→ CRM lookup/create policy → Call context
```

Не считать входящий caller ID надёжным уникальным идентификатором без нормализации и проверки дублей.

## 5. Исходящие звонки

| Аспект | Правило |
|---|---|
| Инициатор | Пользователь с подтверждённым правом и доступным способом звонка |
| Исходящий номер | Выбор по политике компании и поддерживаемой настройке |
| Клиент | Номер берётся из разрешённого CRM-поля |
| Фиксация | Связь с правильной сущностью и ответственным |
| Результат | Статус/запись доступны только в рамках выбранной модели |

```text
CRM card → Employee initiates → Bitrix24/connector → Provider → Customer
```

Массовые обзвоны и автоматические вызовы не предполагаются без отдельного официального механизма, правового основания и нагрузочного проекта.

## 6. Карточка звонка

| Данные | Архитектурный смысл |
|---|---|
| Направление/время | Контекст события и SLA |
| Участники | Пользователь и найденный клиент |
| CRM-связь | Лид, контакт, компания или сделка по формальному правилу |
| Результат | Принят/пропущен/завершён и доступные итоги |
| Запись | Ссылка/доступ в поддерживаемом сценарии, не копия в Git |

```text
Telephony event → Call context → CRM relation → Activity/timeline
```

Карточка звонка не должна раскрывать закрытую CRM-сущность пользователю без соответствующего права.

## 7. Автоматическое создание CRM-сущностей

| Сценарий | Допустимая политика |
|---|---|
| Найден один клиент | Связать звонок с существующим объектом по настроенному правилу |
| Не найден | Создать лид/другой объект только если это подтверждено настройкой и моделью CRM |
| Найдено несколько | Не выбирать случайно; очередь ручной проверки/формальное правило |
| Повторный звонок | Не создавать дубль, если активное обращение уже существует по политике |

```text
Normalized phone → 0 matches: create policy
                 → 1 match: link
                 → N matches: conflict policy
```

Лид не создаётся автоматически «по умолчанию» в архитектуре — это бизнес-решение с критерием дубля и ответственным.

## 8. Распределение звонков

| Метод | Когда применять | Риск |
|---|---|---|
| Группа/очередь | Несколько сотрудников обслуживают линию | Неактуальный состав и отсутствие fallback |
| Ответственный CRM | Нужна continuity клиента | Ответственный недоступен |
| Приоритетная роль | VIP/служебные сценарии при наличии настройки | Избыточная сложность и дискриминационные правила |
| Последовательное/параллельное распределение | Только если поддержано настройкой | Перегрузка или задержка ответа |

```text
Call → Routing policy → eligible employees → selection → fallback
```

Точный алгоритм распределения и параметры **требуют проверки** на портале.

## 9. Очереди

| Компонент | Требование |
|---|---|
| Состав | Роли/пользователи актуальны |
| Eligibility | Статус доступности и права проверяются |
| Waiting | Внутренний SLA и пользовательский сценарий |
| Overflow | Резервная группа, сообщение или иной поддерживаемый выход |
| Metrics | Answered, missed, wait time и backlog — по доступной аналитике |

```text
Primary queue → overflow condition → backup route → missed-call process
```

Очередь телефонии не равна message queue интеграционного middleware.

## 10. Рабочее время

| Настройка | Контроль |
|---|---|
| Timezone | Портал, подразделение и оператор согласованы |
| Schedule | Рабочие дни, интервалы, исключения |
| Holidays | Актуальный календарь и владелец обновления |
| Outside hours | Поддерживаемый fallback и уведомление |
| Emergency | Ручное переключение и возврат к штатному режиму |

```text
Call time → timezone/calendar → open: queue | closed: after-hours route
```

Переходы часовых поясов и праздничные дни входят в приёмочные тесты.

## 11. Запись разговоров

| Область | Требование |
|---|---|
| Доступность | Зависит от способа подключения, тарифа, региона и провайдера |
| Правовое основание | Согласование с применимыми требованиями и уведомлением участников |
| Доступ | Минимальные роли; отдельно от общего доступа к CRM |
| Хранение | Место, срок, удаление, резервирование и объём |
| Экспорт | Только по регламенту; не в репозиторий |
| Аудит | Кто прослушивал/выгружал — в доступной модели |

```text
Call media → provider/Bitrix24 storage policy → role-based access → retention/delete
```

Запись не используется как единственный источник бизнес-результата звонка.

## 12. Поиск клиента

| Шаг | Правило |
|---|---|
| Нормализация | Единый формат страны/номера без изменения оригинала |
| Поля | Стандартные телефонные поля приоритетны |
| Множественные номера | Проверить все разрешённые значения |
| Дубли | 0/1/N matches обрабатываются отдельно |
| Скрытый номер | Не создавать фиктивный контакт без политики |

```text
Caller ID → normalize → exact search → deduplicate → link/create/manual
```

Телефон может быть общим, переиспользованным или ошибочным и не является гарантированным уникальным ключом клиента.

## 13. Маршрутизация

| Правило | Пример архитектурного условия |
|---|---|
| По номеру входа | Продажи/поддержка/регион |
| По времени | Рабочий/нерабочий маршрут |
| По CRM-контексту | Ответственный с fallback |
| По доступности | Только eligible employees |
| По неответу | Backup/пропущенный процесс |

```text
Number → Schedule → CRM context → Availability → Primary → Fallback
```

Каждая ветка имеет владельца, тест и конечный исход; циклический перевод запрещён.

## 14. Права доступа

| Роль | Минимальный доступ |
|---|---|
| Оператор | Звонок и CRM-контекст в рамках своей функции |
| Руководитель | Аналитика группы и контроль качества по регламенту |
| Контроль качества | Прослушивание только при основании |
| Телефония admin | Настройка маршрутизации, не обязательно доступ ко всем CRM-данным |
| Integration identity | Только документированные REST-операции |

```text
Identity → Telephony permission ∩ CRM permission ∩ Recording permission
```

Проверяются UI, мобильный клиент, прямые ссылки, записи, экспорт, REST и уволенные пользователи.

## 15. Интеграция с CRM

| CRM-объект | Роль телефонии |
|---|---|
| Лид | Неквалифицированный новый звонок при выбранной модели |
| Контакт | Физическое лицо и его номера |
| Компания | B2B-контекст и общие номера |
| Сделка | Коммерческая возможность, к которой относится звонок |
| Активность/timeline | История и следующий шаг |

```text
Call → identity resolution → CRM context → activity/result → next action
```

Один звонок не должен автоматически создавать одновременно несколько независимых сущностей без формального правила.

## 16. REST и телефония

REST-возможности телефонии применяются только по [официальному справочнику API](https://apidocs.bitrix24.ru/api-reference/) и выбранной модели приложения. Неподтверждённые методы не перечисляются.

| Контроль | Требование |
|---|---|
| Method/event | Подтверждён в текущей версии документации |
| Auth/scope | Минимальные права и отдельный identity |
| Payload | Валидация, минимизация PII |
| Reliability | Timeout, retry classification, idempotency |
| Volume | Queue, rate control, monitoring |

```text
Telephony app/service ↔ documented REST contract ↔ Bitrix24 ↔ CRM
```

## 17. Webhooks и телефония

| Поток | Контроль |
|---|---|
| Bitrix24 → receiver | Только поддерживаемое событие, queue и deduplication |
| Service → Bitrix24 | Входящий webhook/OAuth как credential, secret storage |
| Replay | Event/operation key |
| Unknown result | REST reconciliation |
| Security | Не предполагать подпись или IP allowlist без контракта |

```text
Event → HTTPS receiver → durable queue → worker → REST enrichment/update
```

Подробности: `knowledge/webhooks/README.md`.

## 18. Smart Processes и телефония

| Сценарий | Допустимая архитектура |
|---|---|
| Сервисная заявка | Звонок связывается с существующим/новым элементом по формальному правилу |
| Объект/оборудование | Идентификация через клиента и предметную связь, не только номер |
| Контроль качества | Создать задачу/элемент после подтверждённого события |
| Эскалация | Smart Process хранит бизнес-цикл, звонок — коммуникацию |

```text
Call → CRM customer → Smart Process relation → task/workflow
```

Нативность связи звонка с конкретным типом Smart Process и доступная автоматизация **требуют проверки**.

## 19. Производительность

| Риск | Контроль |
|---|---|
| Пиковые звонки | Capacity plan, очередь, fallback |
| Burst событий | Durable message queue и rate control |
| CRM-поиск | Нормализованные поля и контроль дублей |
| Записи | Storage, retention, bandwidth |
| REST limits | Актуальная [документация](https://apidocs.bitrix24.ru/), без выдуманных чисел |

```text
Peak load → route capacity → queue/overflow → alert → recovery
```

Нагрузочный тест выполняется синтетическими звонками и согласованным тестовым контуром.

## 20. Безопасность

| Контроль | Требование |
|---|---|
| SIP credentials | Secret manager, ротация, отсутствие в Git |
| TLS/transport | По официальным возможностям провайдера и коннектора |
| Caller data | Персональные данные, минимизация и права |
| Recordings | Legal basis, RBAC, retention, audit |
| Logs | Маскировать номера, credentials и payload |
| Contractors | Временный минимальный доступ |
| Environments | Раздельные test/prod credentials и номера |

```text
Credential → runtime only
Call metadata/recording → least privilege → retention → deletion
```

## 21. Cloud vs On-Premise

| Возможность | Облако | Коробка | Комментарий архитектора |
|---|---|---|---|
| Аренда номера | По региону/тарифу | Зависит от доступного сервиса | Проверить портал |
| SIP-коннектор | Поддерживаемая Cloud-модель | Зависит от версии/конфигурации | Provider compatibility |
| REST-приложение | Через поддерживаемое приложение | Через совместимое приложение | Функции различаются |
| Server code | Нет | Supported modules | Не менять ядро |
| Network/PBX control | У провайдера/внешней АТС | Может быть у владельца | Требует telecom operations |
| DB/logs | Нет прямого доступа | Контроль владельца | Не писать напрямую в БД |
| Cron/agents | Не управляются клиентом | Управляются владельцем | Monitoring обязателен |
| Updates | Vendor-managed | Owner-managed | Stage/backup/regression |

```text
Cloud: provider/connectors ↔ managed Bitrix24
Box: provider/PBX ↔ owned infrastructure ↔ Bitrix24 modules
```

Источник коробочной архитектуры: [официальная документация](https://dev.1c-bitrix.ru/docs/portal.php).

## 23. Практический чек-лист архитектора

| Область | Критерий готовности |
|---|---|
| Контекст | Cloud/Box, region, tariff, provider и connection type подтверждены |
| Номера | Owner, purpose, inbound/outbound policy |
| Routing | Schedule, queues, responsible, overflow, fallback |
| CRM | Lookup, 0/1/N match, create/link, duplicate policy |
| Records | Availability, legal basis, rights, storage, retention |
| Security | SIP secrets, rotation, contractor access, environments |
| Reliability | Capacity, outage, retry, queue, monitoring |
| Support | SLA, contacts, diagnostics, recovery, changelog |

```text
Discovery → Scheme → Provider validation → Security review
          → Synthetic pilot → Acceptance matrix → Production/support
```

- [ ] Все входящие/исходящие номера инвентаризированы.
- [ ] Способ подключения подтверждён официально.
