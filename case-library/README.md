# Bitrix24 Architecture Case Library

Case Library — библиотека обезличенных референсных архитектур для типовых отраслевых и функциональных задач Bitrix24. Кейс показывает ход инженерного решения, а не готовую конфигурацию, которую можно без анализа перенести на любой портал.

> Все данные синтетические. Возможности Bitrix24, зависящие от Cloud/On-Premise, тарифа или редакции, версии, прав, приложения, региона или провайдера, проверяются по официальным источникам и на целевом портале.

## Назначение

- обучение Solution Architect и Business Analyst;
- подготовка структуры коммерческого предложения без реальных цен;
- аудит существующего решения по референсной модели;
- проектирование AS IS и TO BE;
- повторное использование паттернов, тестов и эксплуатационных практик;
- фиксация trade-offs, рисков и ADR.

## Структура кейса

```text
Бизнес -> Требования -> Архитектура -> Реализация
 -> Тестирование -> Deployment -> Monitoring -> Улучшение
```

| Слой | Обязательное содержание |
|---|---|
| Бизнес | Контекст, цели, проблемы, stakeholders, ограничения |
| Требования | Scope, out of scope, KPI, роли, данные, исключения |
| Архитектура | Сущности, lifecycle, права, master data, интеграции, ADR |
| Реализация | Конфигурация, automation, contracts, mapping |
| Тестирование | Positive, negative, repeat, recovery, UAT |
| Эксплуатация | Deployment, monitoring, support, rollback, roadmap |

## Правила использования

1. Начинать с Discovery целевого портала и не копировать конфигурацию вслепую.
2. Проверять Cloud/On-Premise, тариф/редакцию, версию, права и доступные приложения.
3. Использовать только обезличенные или синтетические примеры.
4. Не хранить секреты, webhook URL, реальные домены, CRM ID и клиентские выгрузки.
5. Назначать мастер-систему для каждого типа данных.
6. Для массовых операций использовать dry-run, test sample, idempotency и rollback.
7. Фиксировать ключевые решения через ADR.
8. Завершать кейс test plan, deployment, monitoring и residual risks.

## Критерии качества кейса

- цель измерима;
- AS IS отделён от TO BE;
- сущности выбраны обоснованно;
- факты отделены от рекомендаций;
- права и безопасность рассмотрены;
- integrations имеют ownership, errors и monitoring;
- testing и rollback практически выполнимы;
- ограничения и открытые вопросы перечислены;
- источники официальные и зарегистрированы в `knowledge/SOURCES.md`.
